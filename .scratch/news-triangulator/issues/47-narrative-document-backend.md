# 47 — Cross-Source Narrative: Structured NarrativeDocument (Backend)

**What to build:** Replace the Cross-Source Narrative's current flat `DimensionItem[]`/segments
representation with a structured `NarrativeDocument` — blocks (heading/paragraph/quote/list) built
from inline text/entity/source/value runs, plus `NarrativeAssertion`s citing back to specific,
stably-identified Analysis Dimension items. Analysis Dimensions remain authoritative and computed
first (ADR 0012, unchanged) — this only replaces how the Narrative pass represents and verifies its
own output. See [ADR 0034](../../../docs/adr/0034-structured-narrative-document.md) and
`CONTEXT.md`'s Cross-Source Narrative / Narrative Assertion entries.

**Blocked by:** none — `StoryEntity`/`StoryEntityRelation` (ADR 0024), Analysis Dimensions
(ADR 0001/0030), and the existing `narrative.generate` job (ADR 0028) already exist.

**Status:** ready-for-agent

- [ ] `DimensionItem`/`ContradictionItem` gain a stable `id`, generated once at Synthesis time and
      persisted — never an array index (which wouldn't survive `verifyAndRepair` reshuffling
      arrays on retry).
- [ ] New shared types per ADR 0034's exact shapes: `NarrativeDocument`, `NarrativeBlock`
      (`heading`/`paragraph`/`quote`/`list`), `NarrativeInline` (`text`/`entity`/`source`/`value`),
      `NarrativeAssertion`, `NarrativeEntityRef`, `NarrativeSourceRef`, `NarrativeValueRef`. A
      `quote` block carries exactly one `sourceId` (never an array) — one verbatim quotation, one
      origin.
- [ ] Narrative LLM call switches from today's loose `json_object` mode to strict `json_schema`
      Structured Outputs (model choice: whatever's actually configured via `SYNTHESIS_MODEL` at
      implementation time, not hardcoded to a specific model name). Prompt updated to emit
      transport-only `<nt:e>`/`<nt:v>`/`<nt:s>` markup inside block text, plus the
      `assertions`/`entityRefs`/`sourceRefs`/`valueRefs` arrays — each assertion citing a real
      `dimensionItemId`.
- [ ] `verifyAndRepair` (ADR 0014) extended with the new semantic checks this document shape needs:
      a ref (entity/source/value) that doesn't resolve to a declared top-level ref, a `quote`'s text
      that isn't a verbatim substring of its one cited Source's text, an assertion citing a
      nonexistent `dimensionItemId`. On failure: retry the *whole document* once (not a per-item
      retry — there's no meaningful way to drop one block from an otherwise-coherent narrative); a
      second failure fails the job and falls back to `narrative.generate`'s existing pg-boss retry
      (ADR 0028). A `NarrativeDocument` is never persisted partially valid.
- [ ] Inline `<nt:...>` markup is parsed into the `NarrativeInline` AST exactly once, immediately
      after verification passes; only the parsed structure is ever persisted to
      `SynthesisResult.narrative` — never raw markup strings in a stored block's text.
- [ ] Deterministic Czech-numeral parser derives `NarrativeValueRef.normalizedValue`/`unit` from
      `text` server-side, as a post-processing step after the LLM call returns (the LLM itself only
      ever emits `text`/`sourceIds`, never the normalized number). `normalizedValue`/`unit` are
      `null`/`null` when the text can't be safely parsed, rather than guessed.
- [ ] `SynthesisResult.narrative`'s shape changes in place — one canonical narrative
      representation, no dual-format period. Every historical COMPLETE Analysis gets its narrative
      regenerated by re-enqueuing the existing `narrative.generate` job (ADR 0028), not a bespoke
      migration script.
- [ ] `AnalysisDetail`/`AnalysisContext` gains `entities`/`entityRelations` — the full Story-level
      `StoryEntity`/`StoryEntityRelation` set, not filtered down to only what the narrative
      referenced inline (the point of surfacing this is showing subjects the prose didn't dwell
      on).
- [ ] Tests: Zod schema validation of the new document shape; each new `verifyAndRepair` semantic
      check (dangling ref, non-substring quote, dangling `dimensionItemId`), including the
      whole-document-retry-then-job-failure path; the Czech-numeral parser as a pure unit
      (including unparseable text → `null`); an integration test confirming a backfilled Analysis's
      narrative round-trips end to end through the new pipeline.

## Notes

Frontend rendering (replacing ticket 20's shipped `NarrativeArticle` component) is deliberately
split into a separate ticket (48), blocked by this one — mirrors the ticket 40/46
backend-then-UI precedent this project already established.

`NarrativeAssertion` is named to avoid colliding with this codebase's existing `Claim` vocabulary
(Extraction's Factual/Attributed/Interpretive statements) — see CONTEXT.md.

"Use entities sparingly" (most candidate entities should not get an inline tag; the same entity is
typically tagged only at its first significant mention) is a prompt instruction only in this wave —
no deterministic dedup/cap enforcement. Revisit only if over-tagging turns out to be a real problem
in practice.
