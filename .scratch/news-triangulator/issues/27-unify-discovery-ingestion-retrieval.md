# 27 — Unify Discovery and Ingestion Into One Retrieval Pipeline

**What to build:** Today two independent retrieval mechanisms find Coverage for the app: human-seeded **Discovery** (`discoverCoverage`/`extractKeywords` — GDELT + RSS, LLM-driven keyword search, triggered when a user submits a Seed Article on `HomePage`) and automated **Ingestion** (embedding-similarity matching against recently-open Stories, no LLM on the hot path — ADR 0018/ticket 23). This ticket is to design and build **one shared retrieval mechanism** underneath both, so there is a single, well-documented pipeline doing the actual coverage-finding work — while keeping **both entry points** (a human pasting a URL, and the background cron finding one on its own). Not a single entry point: retiring manual seed-URL submission was explicitly considered and rejected — Discovery and Ingestion solve genuinely different problems (targeted investigation of a specific story vs. passive monitoring of outlets already covered by Ingestion), and collapsing the trigger would remove real capability (investigating a story from an outlet Ingestion doesn't monitor, or one that happened before Ingestion caught it).

**Blocked by:** None directly, but **not ready for an implementing agent yet** — see Status. The mechanism choice below needs its own design pass before this is buildable.

**Status:** blocked — mechanism choice (embeddings-only vs. LLM search vs. hybrid) not yet decided; needs a dedicated design session before an implementing agent picks this up, same as ticket 26 started

- [ ] Mechanism choice made and recorded as an ADR (next number after 0018) — this is the core open question and is genuinely hard to reverse: Ingestion's embedding-only approach exists specifically to keep every-~20-minute polling cheap (ADR 0018); Discovery's LLM keyword search exists because a human is waiting in real time and can tolerate (and benefits from) a more expensive, higher-quality search. Candidate directions to weigh, not a prescribed answer:
  - Standardize both paths on embeddings — cheapest, but may weaken Discovery's real-time match quality for a human actively investigating a story
  - Standardize both paths on LLM keyword search — better quality, but re-introduces an LLM call (and GDELT/RSS search) onto Ingestion's hot path, defeating the cost reason ADR 0018 exists
  - A hybrid: embeddings for cheap candidate generation, an LLM verification pass only when a candidate is ambiguous or a human is waiting synchronously (Discovery) — closest to what Ingestion already does at Draft-approval time (ticket 18's bulk verification pass), just extended earlier in the pipeline
- [ ] Human-seeded Stories (`analysisRepo.createAnalysis`) gain an embedding at creation time, closing the known gap (flagged in ticket 23's notes) where Ingestion's matching pool can't recognize a human already started investigating a Story — a real prerequisite for calling this "one pipeline," not an optional extra, since without it Ingestion still can't see human-seeded Stories no matter what mechanism wins above
- [ ] Backfill strategy decided for existing human-seeded Analyses that predate this change (compute embeddings lazily on next match attempt vs. a one-off migration script vs. leaving pre-existing ones unmatched going forward)
- [ ] Discovery (`discoverCoverage`/`extractKeywords`) and Ingestion's matching path converge on the shared mechanism chosen above, with both entry points (`HomePage` seed submission, the Ingestion cron) still producing a Draft/Analysis + Story the same way they do today
- [ ] `CONTEXT.md`'s `Discovery` and `Ingestion` entries updated to describe the unified mechanism underneath, while keeping the two entry-point definitions distinct (they remain genuinely different concepts — see rejected single-entry-point option above)
- [ ] README's description of Discovery vs. Ingestion (added in ticket 28) updated to reflect the unified mechanism once built

## Notes

Scoped out of a `/grill-with-docs` session (2026-08-17) that started as a navbar bug report and a local-dev-workflow question, and surfaced that the project owner considers the current two-mechanism split an "old way of doing it" worth fixing — but explicitly not by removing manual seed-URL submission (considered and rejected in that session; see the rejected option above). Kept as its own ticket rather than resolved in that session, for the same reason ticket 26 was split from ticket 22: the mechanism choice is a real, hard-to-reverse architectural trade-off (cost vs. quality, per-path) that deserves a dedicated design pass, not a same-session decision.

Session investigation (read-only code audit, not a live run) confirmed: the existing Draft → approve → Review Step → Analysis pipeline itself is not broken by the two-mechanism split — both paths converge on the same `Analysis`/`Coverage` model and the same shared `STATUS_MAP` mapper today. This ticket is about consolidating the *retrieval* mechanism for quality/maintainability/documentation reasons, not fixing a defect in how the two paths currently coexist.
