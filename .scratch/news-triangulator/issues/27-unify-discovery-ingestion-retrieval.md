# 27 — Unify Discovery and Ingestion's Same-Event Classification; Dedup on Submission

**What to build:** Human-seeded **Discovery** and automated **Ingestion** don't actually source candidates the same way, and a follow-up design session (2026-08-17, see Notes) concluded they shouldn't — GDELT/RSS-search-for-a-specific-seed and continuous-RSS-polling-with-no-target answer genuinely different questions. What *was* genuinely duplicated: two independent implementations of "does this candidate describe the same real event as an anchor headline?" — Discovery's per-candidate LLM call (`verifySameStory`) and Ingestion's embedding-similarity threshold (ADR 0018). This ticket unifies that one shared question, at different cost budgets per caller, and — since the fix closes the embedding gap that was blocking it — adds the dedup check human-seeded submission never had: checking whether a submitted seed URL already matches an open Story (from Ingestion or an earlier submission) before creating a duplicate. See ADR 0019.

**Blocked by:** None.

**Status:** done

- [x] Mechanism choice made and recorded as an ADR (0019) — resolved narrower than the three original candidate directions (embeddings-only / LLM-only / hybrid) suggested: unify the *classification* question only, not the sourcing mechanisms. Discovery affords an LLM confirmation on top of the shared embedding pre-filter (rare, real-time, human-waited); Ingestion's hot path is unchanged (embedding-only, LLM deferred to Draft approval, per ADR 0018) — nothing about its cost profile changed, so nothing about its mechanism needed to.
- [x] Human-seeded Stories (`analysisRepo.createAnalysis`) gain an embedding at creation time, closing the known gap (flagged in ticket 23's notes) where Ingestion's matching pool couldn't recognize a human already started investigating a Story — this fell out of unifying the classification step for free, since both callers now need the same embedding representation.
- [x] Backfill strategy decided: none needed. The 48h matching window (`DEDUP_WINDOW_HOURS`) makes any Story older than that already irrelevant to matching, embedding or not.
- [x] Discovery and Ingestion's same-event *classification* converge on the shared `findBestMatch` embedding core, with sourcing deliberately left separate (see reframe in What to build) — both entry points still produce a Draft/Analysis + Story the same way they did before.
- [x] `CONTEXT.md`'s `Discovery`, `Ingestion`, and `Story` entries updated to describe the shared classification step, keeping the two entry-point definitions distinct.
- [x] README's Discovery-vs-Ingestion section updated, with a Mermaid diagram of the shared classification flow.
- [x] **New, added during the design session** (see Notes — the original checklist didn't anticipate this): human-seeded submission (`POST /api/analyses`) now checks for an existing match before creating anything, via the same classification step. A confirmed match returns `{ outcome: 'matched' }` instead of creating a duplicate; the Admin gets a confirm/override screen (`HomePage`'s new `matched` step) rather than a silent redirect. Continuing with a DRAFT/PENDING match attaches the seed as Coverage (`POST /api/analyses/:id/attach-seed`) and, for DRAFT, runs the existing `approveDraft` flow inline. Continuing with a COMPLETE match navigates straight to the existing Analysis. A `force: true` override skips the check entirely. Tests: `analysisService.test.ts` covers matched/rejected/FAILED-treated-as-no-match/force/embedding-failure-degrades-gracefully for `createAnalysis`, and PENDING/DRAFT/not-found/wrong-status for `attachSeedToMatch`.

## Notes

Scoped out of a `/grill-with-docs` session (2026-08-17) that started as a navbar bug report and a local-dev-workflow question, and surfaced that the project owner considers the current two-mechanism split an "old way of doing it" worth fixing — but explicitly not by removing manual seed-URL submission (considered and rejected in that session).

A second `/grill-with-docs` session (also 2026-08-17, once ticket 28 shipped) did the actual design work this ticket was blocked on. It reframed the original checklist's "one shared retrieval mechanism" into something narrower and more defensible after a code audit found candidate *sourcing* (Discovery's GDELT/RSS search vs. Ingestion's RSS polling) and same-event *classification* (the actual duplicated logic) were being conflated — see "What to build" above. That reframe is why several checklist items above read differently than the ticket was originally filed with; the underlying goal (one well-documented pipeline, human-seeded Stories recognized by Ingestion) is unchanged. The same session also surfaced and scoped in the submission-dedup gap, since the project owner explicitly wanted it in this ticket rather than split out further ("one pipeline, just two kinds of input").

Session investigation (read-only code audit, not a live run) confirmed: the existing Draft → approve → Review Step → Analysis pipeline itself is not broken by the two-mechanism split — both paths converge on the same `Analysis`/`Coverage` model and the same shared `STATUS_MAP` mapper today. This ticket consolidates the *classification* mechanism for quality/maintainability/documentation reasons (plus the submission-dedup gap it enables), not a defect in how the two paths currently coexist.

## Implementation (2026-08-17)

A local code-review caught and fixed five real issues before commit: (1) `attachSeedToMatch` decided whether to call `approveDraft` using the Analysis status read before the (network-call) scrape, not a fresh read — a concurrent approve/reject via the Ingestion review queue could leave a Coverage row committed on an Analysis that had since changed status; fixed with a fresh status re-check immediately before writing. (2) The same function inserted a Coverage row unconditionally, risking a second Coverage from the same outlet on one Analysis (`CONTEXT.md`'s "one Coverage per Source" invariant); fixed to skip the insert (but still approve, if DRAFT) when that outlet is already attached. (3) `POST /api/analyses` always returned 201, even for a `'matched'` outcome that creates nothing; fixed to return 200 for `matched`, 201 only for `created`. (4) `confirmCoverages`'s custom-URL handling had its own inline hostname-extraction regex duplicating `extractDomain`, which this ticket's `attachSeedToMatch` already imports; consolidated onto the one shared function. (5) Two comments went stale during the diff itself — `storyMatching.ts` still pointed at `DEDUP_WINDOW_HOURS`'s old home in `ingestionService.ts` after this ticket moved it, and `schema.prisma`'s `Story.embedding` comment still said the field was Ingestion-only after this ticket made it universal; both corrected.

Two more findings were judged real but not worth fixing here, and are documented as accepted limitations in ADR 0019's Consequences section instead: a TOCTOU race in the submission dedup check (two admins submitting the same/an equivalent URL within a few seconds could both create a Story — the same class of imperfection Ingestion's own matching already accepts, and no worse than today's false-negative status quo), and `attachSeedToMatch` re-scraping a URL `createAnalysis` already scraped moments earlier in the same flow (a deliberate consequence of ADR 0004's no-caching stance, not an oversight).
