# Map: Backend Audit Remediation

Label: wayfinder:map

## Destination

A triage decision on every finding in `docs/audit.md` (a 1701-line, Czech-language architectural audit of the backend): for each, decide whether it's a real bug/gap worth fixing now, or a legitimate scale-oriented improvement worth deferring with an explicit, checkable trigger condition — never a silent drop. Reaching the end of this map means every finding has landed in exactly one of: accepted-now (→ implementation tickets in `.scratch/news-triangulator/issues/`), deferred-with-trigger, or ruled out of scope.

## Decisions so far

- [Quick fixes: no-brainers regardless of scale](issues/01-quick-fixes-no-brainers.md) — accepted P0-1 (no indexes), P0-4 (LlmCallLog stores full embedding vectors forever), P2-17 (non-timing-safe secret compare), P2-20 (no curl `--max-time`), P2-26 (integration tests skip push-to-`ticket/**`); split P2-24 (admin audit log) into its own ticket; deferred P1-12 (title-less Coverage misclassified as a verification failure) to pair with P2-23 later; rejected P2-25 (`.scratch/` committed) as not-a-finding — that's this project's deliberate ticket-tracking convention.
- [Source identity: adopt Source/SourceFeed now?](issues/02-source-identity-model.md) — confirmed P0-6 (worse than described: Ingestion's attach path had no duplicate-source check at all, not just inconsistent naming); adopted the full `Source`/`SourceFeed` schema now (not the lighter option initially recommended); fixed at the DB level via a partial unique index, plus the Ingestion collision-check gap. Split P1-13 (no robots.txt/rate-limiting/backoff) into its own ticket.
- [Pagination and request caps](issues/03-pagination-and-request-caps.md) — DB still empty, no usage data to weigh against; built full keyset pagination now (reader listing + Admin draft queue) per the project's future-growth framing. The draft queue's visibility filter had to move from a JS post-filter into a `HAVING` clause (raw SQL) to paginate correctly. Added `MAX_CUSTOM_URLS`/`MAX_COVERAGES_PER_ANALYSIS` caps and fixed P0-2 (bounded Ingestion's known-URL lookback to 30 days instead of the whole table).
- [Entity model: table vs. JSON — revisit ADR 0022?](issues/04-entity-model-table-vs-json.md) — ADR 0022's entity-resolution-avoidance reasoning doesn't rule out a normalized table (the `key` stays a deterministic label either way); adopted `Entity`/`StoryEntity`/`StoryEntityRelation` tables now, recorded as [ADR 0024](../../docs/adr/0024-entity-storage-table-not-json.md) (amends ADR 0022's storage-shape clause only). Fixes P1-9 via IDF-weighted containment. Clean cutover, no `entitiesLegacy`. `storyCount` maintained transactionally only — no correction job, no new dependency on ticket 06. Omitted `EntityAlias`/`wikidataId`/`salience`/trigram search as speculative-generality. Split P1-14+P1-15 into [ticket 11](issues/11-entity-extraction-chunking-and-model-var.md); split salience/fuzzy-search into [ticket 12](issues/12-entity-salience-and-fuzzy-search.md). Unblocks (but does not resolve) [ticket 07](issues/07-thread-aggregate.md)'s `Thread` question. Implemented on `ticket/audit-04-entity-model-table-vs-json`.
- [Retrieval/matching architecture: pgvector + unified scorer, now or trigger-deferred?](issues/05-retrieval-matching-architecture.md) — deferred the full pgvector/HNSW + unified scorer migration; trigger is candidate-pool size per match exceeding 200 (throughput-bound, not tied to total `Story` count, since both matching windows are rolling). Accepted now, independent of the deferral: `MatchDecision` log table (same-event matching only, not `StoryRelation` scoring), P1-7 fix (dropped multiplicative time-decay entirely — it was the actual cause of the 26-34h effective window, not something a redundant filter could fix), and P1-8 fix + a real `EmbeddingCache` for idempotence, recorded as [ADR 0025](../../docs/adr/0025-canonical-embedding-input-and-cache.md). Implemented on `ticket/audit-05-retrieval-matching-architecture`.
- [Async job queue: now or trigger-deferred?](issues/06-async-job-queue.md) — deferred the full Postgres-native job queue; trigger adopted from the audit as-is (≥2 of: >~50 sources, replay-event-history need, more than one independent consumer of the same event). No speculative "prep for the queue" restructuring — today's service functions already look worker-friendly. Accepted now: P0-5 (unauthenticated GET's unbounded narrative-regeneration cost — worse than described, a *failed* generation retried on every subsequent view, not just concurrent ones) fixed via a durable failure marker + 24h TTL-bounded auto-retry, recorded as [ADR 0026](../../docs/adr/0026-narrative-generation-failure-marker.md); P2-22 (no ingestion-run idempotency lock) fixed via `IngestionRunLock`, a single-row lease rather than ticket 04's `entity.ts` advisory-lock pattern — that pattern wraps a short DB-only transaction, and `runIngestionPass` makes long-running external calls that can't safely sit inside one, recorded as [ADR 0027](../../docs/adr/0027-ingestion-run-lock-row-lease-not-advisory-lock.md). Implemented on `ticket/audit-06-async-job-queue`. **Partially reopened by ticket 07** — see below.
- [`Thread` aggregate: now or deferred?](issues/07-thread-aggregate.md) — **build now**, following the audit's design (§7.4/§8.6/§9.8) directly. The underlying multi-stage-arc pattern is confirmed real (observed in tracked source material), not hypothetical — the empty DB is a dev-pruning artifact, not evidence against it. Reopens part of ticket 06's queue deferral: `thread.recompute` has no synchronous fallback, so pg-boss is adopted, scoped to `entity.extract`/`relation.link`, `narrative.generate` (superseding ADR 0026), and `thread.recompute` only — recorded as [ADR 0028](../../docs/adr/0028-pg-boss-job-queue-adoption.md). `Story.eventTime` added as a prerequisite (fixes the rest of P1-11 too) — recorded alongside the `Thread`/`ThreadMember` schema itself in [ADR 0029](../../docs/adr/0029-thread-aggregate.md). Split into five subtickets, none resolved this session: [13](issues/13-pg-boss-job-queue-infrastructure.md) (queue infra, blocks 14/15/17), [14](issues/14-entity-relation-job.md) (entity/relation job), [15](issues/15-narrative-generation-job.md) (narrative job), [16](issues/16-story-event-time.md) (`eventTime`, independent), [17](issues/17-thread-recompute.md) (the aggregate itself, blocked by 13+16).
- [pg-boss job queue infrastructure](issues/13-pg-boss-job-queue-infrastructure.md) — library/deployment shape/scope already settled by ADR 0028; this ticket's own five open questions (job naming/typing, retry defaults, observability, dev workflow, test-migration impact) all resolved by direct application of existing project conventions (no new custom log table — pg-boss's own job/archive tables suffice; same Dockerfile, different `CMD`; job names as a `JobName` const, not strings). Implemented on `ticket/audit-13-pg-boss-job-queue-infrastructure`.
- [Entity extraction + relation linking as a queued job](issues/14-entity-relation-job.md) — `approveDraft`/`confirmCoverages` enqueue `JobName.EntityRelation` and return immediately, no synchronous wait. Job handler stops using today's swallow-everything pipeline contract: permanent failures (Analysis/Story gone) are logged and swallowed, retryable ones (LLM/DB) are logged with stage context and rethrown as `ExternalServiceError` so `LLM_JOB_RETRY_POLICY` (ticket 13) actually retries — data writes (`replaceStoryEntities`, `createStoryRelation`) already idempotent by construction, so a retry is safe though not free (a redundant LLM call if extraction already succeeded before a later failure, accepted per ADR 0028's combined-job scope). Payload extended to `{ analysisId, origin: 'draft-approval' | 'coverage-confirmation', coverageIds }` so the handler reproduces each flow's exact source-text selection (`extractedText` → `title` unless `EXTRACTION_FAILED` → skip) over exactly the Coverage rows eligible at enqueue time — not any Coverage attached to the Analysis afterward, which would otherwise leak never-verified content into extraction — and preserves today's `anchorHeadline` asymmetry rather than changing extraction inputs. Implemented on `ticket/audit-14-entity-relation-job`.
- [Narrative generation as a queued job](issues/15-narrative-generation-job.md) — supersedes ADR 0026 with the audit's originally-intended fix: `narrative.generate` is enqueued inside the same transaction that flips an Analysis to COMPLETE (`completeAnalysisWithSynthesis` gains an `onComplete` transaction callback, same seam ticket 14 established), so `getAnalysisDetail` becomes pure DB reads and no unauthenticated GET ever triggers an LLM call again. `narrativeGenerationFailedAt` is retained but demoted to a pure audit trail — nothing reads it back to gate a retry any more, `LLM_JOB_RETRY_POLICY`'s bounded 3-attempt retry is the only retry mechanism now (accepted: a persistently-failing Analysis no longer gets ADR 0026's indefinite 24h-cadence retries, deliberately bounded instead). `inFlightNarrativeGenerations` removed as dead code. No distinct "generating" state added for the narrow COMPLETE-but-not-yet-narrated window — `AnalysisPage` already renders "no narrative" the same way for pending/failed/never-attempted, and this window is shorter than before (a job pickup, not a blocking first-view LLM call). Implemented on `ticket/audit-15-narrative-generation-job`.
- [`Story.eventTime`](issues/16-story-event-time.md) — `Story` gains a nullable `eventTime` column (no default, no backfill — matches `embeddingModel`/`embeddingInputHash`'s precedent, per ADR 0029's own Consequences), populated from `CandidateArticle.publishedAt` (RSS `pubDate`) for Ingestion-originated Stories, left `null` for human-seeded ones (`scrapeArticle` extracts no structured publish date, and building per-site date parsing was declined as speculative, ADR 0009). Fixes P1-11's other half: `storyRelationPass.ts`'s `confirmStoryRelation` now sends `eventTime ?? createdAt` under `publishedAt` instead of bare `createdAt`, and `storyRelationScoring.ts`'s time-decay score uses the same fallback — both consumers the audit's own P1-11 fix names (`docs/audit.md:580`), not just the LLM payload. The candidate-window *query bounds* deliberately still anchor to `createdAt`, unrelated to accuracy: that anchor protects `StoryRelation`'s directional-edge invariant, a correctness guarantee this ticket doesn't touch. A `/code-review` pass caught two deviations from ADR 0029 in the first implementation draft (nullability, and GDELT wrongly claimed as an Ingestion source) — corrected in the ticket's own Answer and in a short amendment note added to ADR 0029 itself. Implemented on `ticket/audit-16-story-event-time`.
- [`Thread`/`ThreadMember` + `thread.recompute`](issues/17-thread-recompute.md) — the aggregate itself, per ADR 0029's already-settled schema and recursive-CTE recompute mechanism (§8.6). `thread.recompute`'s payload corrected from ticket 13's placeholder `{ threadId }` to `{ seedStoryId }` (a Thread may not exist yet when the triggering edge is confirmed); enqueued (non-atomically, a deliberate downgrade from tickets 14/15/16's atomic-callback pattern — see the ticket's own Answer) from both real trigger points ADR 0028 names: `linkStoryRelations`'s auto-linking and `approveStoryRelation`'s Admin approval (ticket 36), whenever a `StoryRelation` reaches `FOLLOW_UP`/`PUBLISHED`. `inferRole` narrows to first=`ORIGIN`, last=`RESOLUTION` only at ≥3 members, else `DEVELOPMENT` — `REACTION` is declared in the schema (matching ADR 0029) but never inferred, too fragile a signal to build reliably from `StoryRelation.reasoning`'s free text for a presentation-only label. `Thread.title` is LLM-derived once, at creation, from Agreement flattened across every member (`threadTitlePass.ts`, reusing `SYNTHESIS_MODEL`), skipped entirely (no billed call) on a recompute of an already-existing Thread since its title is never regenerated; a title-generation failure on genuine creation falls back to the `ORIGIN` member's own display title instead of failing the job. `upsertThreadFromComponent` also merges two pre-existing Threads that a new edge bridges (earliest-`firstEventAt` survives) and early-exits when a recompute finds nothing actually changed. Reader surface shipped now, not deferred — `AnalysisDetail` gains an optional `thread` field (title/memberCount/members, `COMPLETE`-only, no `role` exposed) as a small addition to ticket 37's existing Related Events section, deliberately avoiding a repeat of the audit's own §2.3 "Event Graph shipped with no reader surface" mistake. Explicitly deferred, not built: `DORMANT → CLOSED`'s admin surface, a homepage "all ACTIVE Threads" view, and — caught only by `/code-review`, not decided up front — ADR 0029's *entity-configuration-overlap* `DORMANT → ACTIVE` revival path for a case resuming outside the normal 14-day candidate window (the *ordinary* revival, via a fresh in-window edge, is implemented; the entity-overlap path is a second, real matching pathway worth its own ticket). Two `/code-review` rounds; the first caught a real crash (merging two Threads a bridging edge unifies previously threw on `ThreadMember.storyId`'s unique constraint, identically on every retry), a wasted billed LLM call on every recompute of an existing Thread (not just its creation, contradicting this ticket's own stated design), non-chronological Agreement fed to the title LLM call, and the DORMANT-revival overclaim itself — all fixed or corrected above. Implemented on `ticket/audit-17-thread-recompute`.
