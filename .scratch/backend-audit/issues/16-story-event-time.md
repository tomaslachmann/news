# 16 — `Story.eventTime`

Type: grilling
Status: resolved
Blocked by: none — can start immediately (independent of the queue work, tickets 13–15)

## Question

Split from [Thread aggregate](07-thread-aggregate.md) via [ADR 0029](../../../docs/adr/0029-thread-aggregate.md). `Story` has `createdAt` (row-insert/ingest time) but nothing representing when the real-world event actually happened. Thread's member ordering and role-inference (`ORIGIN`/`DEVELOPMENT`/`REACTION`/`RESOLUTION`) need the latter — the audit is explicit that `createdAt` reintroduces P1-11's distortion (a Draft sitting in the Ingestion review queue for days would order/infer role wrong, and silently reorder later purely because of when it happened to get approved). This also fixes P1-11's other half: `storyRelationPass.ts`'s `confirmStoryRelation` currently sends `createdAt` to the LLM under the field name `publishedAt` when deciding `RELATED` vs. `FOLLOW_UP` — the same new field fixes both consumers.

Not yet decided:

1. Source of truth for `eventTime` at Story creation: the seed article's own published date where available (which sources reliably provide this — RSS `pubDate`, GDELT's own timestamp, a scraped article's byline date?), ingest time (`createdAt`) as fallback where not. Needs a concrete per-source-path decision, not just "best available."
2. Nullable vs. always-populated: given the fallback-to-`createdAt` plan, is there ever a case where `eventTime` is genuinely unknown and should stay null, or does the fallback mean it's always populated (in which case, non-nullable with a default makes more sense than nullable)?
3. Does this ticket also fix `storyRelationPass.ts`'s `publishedAt` mislabeling (sending `eventTime` there instead of `createdAt`), or does that stay a separate, smaller follow-up since it's a different call site than Thread's own ordering?
4. No backfill for Stories created before this field exists, matching this project's established convention (ADR 0022, ADR 0025) — confirm this holds here too, and confirm nothing downstream (Thread ordering, the relation-confirmation prompt) breaks on a pre-migration Story with a null/fallback `eventTime`.

## Answer

*Revised after a `/code-review` pass caught two deviations from [ADR 0029](../../../docs/adr/0029-thread-aggregate.md) in the first draft of this Answer — noted inline below rather than silently rewritten, since ADR 0029 (not this ticket in isolation) is the actual design authority for this field and should have been read in full before drafting Q2/Q1, not just referenced via the map. See ADR 0029's own "Narrowed by ticket 16" amendment note for the reader-facing version of this correction.*

1. **Source of truth, per path**: only two call sites ever create a Story (`analysisRepo.createAnalysis`/`createDraftAnalysis` — Discovery never creates one, only Coverage on an already-seeded Story). Concretely:
   - **Ingestion** (`createDraftAnalysis`, `ingestionService.ts`): `eventTime = item.publishedAt` (`CandidateArticle.publishedAt`, `rss.ts`'s parsed `pubDate`, or RSS's own fetch-time fallback when a feed omits one — an existing degraded case this ticket doesn't change). *Correction: the first draft of this Answer claimed GDELT's `seendate` also feeds this path — wrong. Ingestion's candidate pipeline (`runIngestionPassLocked`) calls only `queryRssFeeds`; `queryGdelt` is exclusively `discovery.ts`'s (Discovery is Coverage-only, never creates a Story). Ingestion's `eventTime` is RSS-only.*
   - **Human-seeded submission** (`createAnalysis`, `analysisService.ts`): left `null`. `scrapeArticle`/`ScrapedArticle` extracts no structured publish date today (Readability's `publishedTime` is unreliable enough across Czech outlets that building and maintaining per-site date parsing is a real, uncertain-value feature — not something this ticket's own question mandates, and speculative beyond what's asked, ADR 0009). *Correction: the first draft defaulted this to submission time (`new Date()`) instead of leaving it null — a fabricated value ADR 0029 doesn't ask for and that silently masks "no real signal" as if it were one. Every real consumer of `eventTime` falls back to `createdAt` at its own point of use (see Q3), which submission time would have approximated anyway but dishonestly, baked in at write time instead of read time.*

2. **Nullable vs. always-populated**: **nullable**, per ADR 0029's own Consequences section ("`Story.eventTime` is nullable-at-the-database-level but always populated going forward... matching this project's established no-backfill convention for additive fields... `embeddingModel`/`embeddingInputHash`"). *Correction: the first draft of this Answer independently reasoned to non-nullable-with-`@default(now())` (matching `Coverage.createdAt`'s precedent instead) without first reading ADR 0029's text, which had already settled this exact question the opposite way. Schema: `eventTime DateTime?`, no default — matches `embeddingModel`/`embeddingInputHash` exactly, not `Coverage.createdAt`. "Always populated going forward" describes Ingestion's real behavior (RSS always yields a timestamp, real or fetch-time-fallback), not a database constraint — human-seeded Stories are the one path where null is the honest, permanent state until/unless byline-date extraction is built later.*

3. **`storyRelationPass.ts`'s mislabeling, and the time-decay score — both fixed now**: `StoryDescriptor` (`storyRelationPass.ts`) gains `eventTime: Date | null` alongside its existing `createdAt: Date`; a shared `eventTimeOrFallback` helper (`eventTime ?? createdAt`) feeds `confirmStoryRelation`'s `publishedAt` JSON value (key name unchanged — the prompt never references the literal key, and "publishedAt" is still an accurate label once given the right value). `storyRelationScoring.ts`'s `ageHours` (the time-decay score) uses the identical `eventTime ?? createdAt` fallback now too. *Correction: the first draft of this Answer scoped the fix to the LLM-payload half only, reasoning the time-decay score was "a different, structural question the ticket doesn't raise." `docs/audit.md:580` directly contradicts that: "teprve tenhle čas patří do time decay a do promptu pro relace" (only this time belongs in the time decay AND in the relation prompt) — opravuje P1-11 names both explicitly, as one fix. Caught by `/code-review`, not self-caught.* `findRelationCandidateStories`'s candidate-window *bounds* (the `beforeStoryCreatedAt`/`since` query filter, not the decay score) deliberately still anchor to `createdAt` — that function's own doc comment explains this protects the `fromStoryId`=newer/`toStoryId`=older directional invariant (`StoryRelation`'s `@@unique` is directional, not symmetric), a correctness guarantee tied to insertion order specifically, not accuracy; switching it to `eventTime` risks two Stories whose `eventTime` and `createdAt` orderings disagree producing a reversed-duplicate edge. Audit's original design (median `publishedAt` over the first N Coverage, computed after Coverage has accumulated) doesn't map onto this codebase's real architecture either — ADR 0018 deliberately never eagerly gathers multi-source Coverage at Story-creation time, so only the seed article's own timestamp exists at the point `eventTime` must be set.

4. **No backfill, confirmed**: nullable with no default (Q2) is itself the no-backfill mechanism — a pre-migration Story simply has `eventTime = null` forever, no separate migration step needed, matching `embeddingModel`/`embeddingInputHash`'s precedent exactly (not `Coverage.createdAt`'s `DEFAULT CURRENT_TIMESTAMP`, which would have fabricated a value for old rows). Nothing downstream breaks on a null `eventTime`: every consumer (`confirmStoryRelation`'s payload, relation-candidate time-decay scoring, and Thread's member ordering once ticket 17 builds it) is required to fall back to `createdAt` at its own point of use rather than assume non-null.

Implemented on `ticket/audit-16-story-event-time`.
