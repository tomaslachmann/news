# 10 — Polite scraping: robots.txt, rate limiting, backoff

Type: grilling
Status: resolved
Blocked by: none — can start immediately

## Question

Spun out of [Source identity: adopt Source/SourceFeed now?](02-source-identity-model.md) — **P1-13** confirmed real while investigating that ticket: `articleScraper.ts`/`articleFetchClient.ts` have no robots.txt check, no per-host rate limiting, and no retry/backoff on failure. Every fetch (seed scrape, custom URL, Discovery candidate, Ingestion RSS item) goes straight to the network with no politeness layer at all.

The `Source` model (now shipped) has room for this — the audit's §7.1 proposed `Source.honorRobots`/`Source.maxRps` fields — but this ticket didn't add them, since nothing would read/write them yet without this work.

Decide:

1. Is per-host politeness worth building now, given current request volume (one seed scrape at a time, RSS polling every 20 minutes across 8 feeds)? Or does it wait until Ingestion's fetch pattern actually causes a problem (rate-limited/blocked by an outlet)?
2. If building now: does it need the full token-bucket + robots.txt-cache design from the audit's §9.7 (`politeFetch`), or does a simpler fixed delay between requests to the same host cover today's actual risk?
3. Where do `honorRobots`/`maxRps`-equivalent settings live — new columns on `Source` (schema migration), or a global constant until a Source ever needs its own override?
4. Retry/backoff on transient failures (429/5xx) — same ticket, or split further?

## Answer

Resolved via a `/grilling` session (interactive, not self-answered). Scope grew beyond the audit's original politeness-only framing: the user brought in a second, related need mid-session — per-`Source` feed-parser selection — plus two concrete data bugs the investigation turned up.

1. **Build now, but the small version, not the audit's full §9.7 `politeFetch` design.** The only concrete failure mode found in code is `confirmCoverages` (`analysisService.ts`) firing `Promise.allSettled` over every PENDING Coverage on an Analysis with no concurrency cap at all — e.g. 25 coverages → 25 simultaneous fetches, possibly to the same host, from one UA, in one second (audit P1-13's own example). Robots.txt on the target outlets (checked directly: `ceskenoviny.cz`, `denik.cz`) already names AI agents (`ClaudeBot`, `anthropic-ai`, `GPTBot`, ...) explicitly under `Disallow`, though the generic `User-agent: *` block this app's UA falls under is permissive on feed/article paths today — so the robots.txt concern is real, not hypothetical, but not yet a reason to build the full crawler-grade honoring machinery.
2. **Small scope, not the token-bucket + robots.txt-LRU-cache design**: a 4-concurrent-fetch cap on `confirmCoverages`'s scrape loop (no per-host limiting — the global cap already throttles two Coverage rows that happen to share a host), retry on 429/5xx up to 3 attempts total (honoring `Retry-After` when present, else fixed 1s/2s backoff, no jitter — traffic here is too low for thundering-herd to be a real risk), and an honest UA string (`NewsTriangulator/1.0 (+https://github.com/tomaslachmann/news)`, replacing the old contact-free `NewsTriangulator/1.0`). No robots.txt check, no per-host token bucket, no `Source.honorRobots`/`Source.maxRps` columns — deferred until a real block/429 incident makes the audit's fuller design worth its own complexity.
3. **No new `Source` config columns for politeness.** The concurrency cap and retry policy are fixed constants in the fetch wrapper, not per-`Source` data — nothing today needs an override.
4. **Retry/backoff: same ticket.** Building the fetch wrapper twice (once for the concurrency cap, again later for retry) would be wasted work — both live in the same `articleFetchClient.ts` change.
5. **Scope addition — per-`Source` (really per-`SourceFeed`) parser selection.** New `SourceFeed.parserKind` column, a string enum, `"rss2"` as the only value for now. Verified empirically, not assumed: all 13 outlets on the user's MVP feed list (existing 8 plus Deník N, E15, Echo24, České noviny/ČTK, CNN Prima NEWS) were fetched and inspected directly — every one has root element `<rss version="2.0">`; the `xmlns:atom="..."` namespace several of them declare is only there for one embedded `<atom:link rel="self">` tag (a common RSS convention borrowed from Atom's spec), not evidence the feed itself is Atom-formatted. `rss-parser` (already the only dependency in `rss.ts`) parses all 13 without modification, CDATA fields included. `parserKind` ships now as an extensible dispatch point (today: one handler, `"rss2"`) rather than a bare unused column, so `rss.ts` picks a parser function per feed instead of hardcoding one — new kinds get a new handler only when a real non-RSS-2.0 outlet is actually added, not speculatively.
6. **Data fixes, folded into the same migration** (found while investigating, using the corrected URLs the user supplied and this session verified):
   - Fixed two dead `SourceFeed` rows: `feed-hn` (`https://archiv.hn.cz/rss` 404s) → `https://archiv.hn.cz/?m=rss`; `feed-denik` (`https://www.denik.cz/rss` redirects to an HTML landing page, not a feed) → `https://www.denik.cz/rss/vse.xml`.
   - Widened three feeds to their outlet's all-articles URL, ahead of a planned future per-category feed configuration: `feed-ct24` → `https://ct24.ceskatelevize.cz/rss`, `feed-idnes` → `https://servis.idnes.cz/rss.aspx`, `feed-aktualne` → `https://www.aktualne.cz/rss`.
   - Added 5 new `Source`/`SourceFeed` pairs: Deník N (`denikn.cz`, `https://denikn.cz/feed/`), E15 (`e15.cz`, `https://www.e15.cz/rss`), Echo24 (`echo24.cz`, `https://www.echo24.cz/rss/s` — the user's originally-given `https://echo24.cz/rss` 404s), České noviny/ČTK (`ceskenoviny.cz`, `https://www.ceskenoviny.cz/sluzby/rss/zpravy.php`), CNN Prima NEWS (`cnn.iprima.cz` — deliberately not the bare `iprima.cz` apex, which also serves unrelated non-news iPrima verticals that `resolveSource()`'s suffix match would otherwise misattribute to this Source — `https://cnn.iprima.cz/rss`).
7. **GDELT (`gdeltClient.ts`) and RSS polling (`rss.ts`'s own fetch, via `rss-parser`) are explicitly out of scope for the fetch-wrapper/retry work** — only `articleFetchClient.ts` (the one behind `confirmCoverages`'s real fan-out risk) is wrapped. GDELT needs its own future ticket: a `latest.txt`-then-CSV-download flow entirely unlike a single-URL fetch, not something this ticket's wrapper generalizes to. `rss.ts`'s 8–13 parallel feed polls are a small, fixed, non-user-triggered set, and `rss-parser` doesn't expose a fetch hook to intercept cleanly — left as-is unless a real problem shows up there.

Recorded in [ADR 0032](../../docs/adr/0032-polite-scraping-small-scope.md).

A `/code-review` pass caught five real issues, four fixed: an outlet-supplied `Retry-After` header had no upper bound, so a hostile/misconfigured `Retry-After: 86400` would make `fetchArticleHtml` — awaited synchronously inside the `confirmCoverages` PATCH handler — hang for nearly a day (capped at 10s); a retryable non-OK response's body was never drained before the next attempt, risking held-open keep-alive connections under retry (now `res.body?.cancel()`s it); `isKnownParserKind` used the `in` operator against a plain object, so a `parserKind` of `"constructor"` would resolve to `Object.prototype`'s inherited value instead of a real handler (switched to `Object.hasOwn`); CONTEXT.md's `SourceFeed` entry hadn't been updated for the new `parserKind` concept, contradicting root CLAUDE.md's own maintenance rule (added). A fifth finding — capping concurrency to 4 while adding a 3-attempt retry raises `confirmCoverages`'s worst-case wall-clock time well above its old ~12s ceiling, an interaction the grilling session's Q9/Q10 answers didn't weigh against each other — is real but not silently fixed by tuning either number against the other; recorded as an explicit, accepted trade-off in ADR 0032's Consequences instead, since both values were the user's own explicit decisions.
