# 12 — Entity salience and fuzzy name search

Type: grilling
Status: resolved
Blocked by: 04

## Question

Spun out of [Entity model: table vs. JSON](04-entity-model-table-vs-json.md) — the audit's §7.3/§8.5 `StoryEntity` schema includes a `salience Float` field ("fraction of this Story's Coverage that mentions the entity") and an `entity_name_trgm` GIN index on `Entity.canonicalName` for fuzzy matching. Neither was built as part of ticket 04's table migration: no salience computation exists anywhere in `entityExtractionPass.ts` today (unlike `confidence`, which is a direct carry-over from the existing JSON shape), and no fuzzy entity-search surface exists to need the index.

Both make sense as their own features, not as unused scaffolding added ahead of anything reading them. Decide:

1. **Salience** — what's the actual product use? The audit frames it as a stronger relation-scoring signal than raw entity-key overlap (an entity every Coverage mentions vs. one mentioned in passing by a single outlet). Is that the motivating use case, or is there a reader/Admin-facing surface that would show it directly?
2. Salience computation needs a per-entity, per-Coverage mention signal — does that require a prompt/schema change to `entityExtractionPass.ts` (currently Story-scoped, not Coverage-scoped, per Coverage output), or can it be derived some other way?
3. **Fuzzy name search** — what surface would use it? An Admin entity browse/search UI doesn't exist yet; is this ticket about building that UI too, or just the index or an accepted trigger for later?
4. Are these two independent enough to split into separate tickets once scoped, or genuinely one ticket?

## Answer

Resolved via a `/grilling` session (interactive, not self-answered). The interview initially found no current building block for either feature: entity extraction is genuinely Story-scoped with no per-Coverage attribution in its LLM output at all (a real prompt/schema change needed for salience, not just a new column); `storyRelationScoring.ts`'s `weightedEntityContainment` has no slot for a per-entity weight beyond IDF (`confidence` isn't even selected by `findStoryEntitiesForScoring` today); and zero entity search/browse UI exists anywhere, reader or Admin. Initial recommendation was to defer both with an explicit trigger, matching ticket 08's product-decision-triage precedent.

**The user overrode that recommendation directly, stating the actual motivation: entities are the seed of a future entity-centric knowledge graph/wiki** — connections, an entity page per entity, eventual Wikidata linking — a materially bigger product direction than `docs/spec-event-graph.md` documents today (that spec explicitly frames entities as Story-scoped relation-scoring evidence only, "explicitly *not* a knowledge graph," with a global entity-resolution/aliasing layer named in its own Out of Scope as a possible *future* wave). Checked `docs/audit.md` directly at the user's request: its §7.3/§8.5 framing ("IDF weighting, entity retrieval, recommendation — exactly the three things entities are extracted for, per the spec") doesn't actually match the spec's own text (no "retrieval"/"recommendation" language exists in `docs/spec-event-graph.md`) — it reads as the audit author's own extrapolation. That said, the spec's Out-of-Scope section independently corroborates the user's stated direction: it explicitly anticipates "a global, cross-Story entity-resolution/aliasing layer" as a distinct, later wave, and says the deterministic key scheme was "designed so this layer can be added later without a data-shape migration" — i.e. the two-wave split (relation-scoring-only now, knowledge-graph later) was already the spec's own intent, just not yet acted on.

1. **Salience: built now.** `entityExtractionPass.ts`'s prompt and `LlmResultSchema` both changed — `userContent` is now an indexed array (`{index, text}[]`, not a bare string array) so the model can report `source_indices` per entity; `runEntityExtractionPass` unions every mention's `source_indices` per deduped entity key and computes `salience = |unique indices| / sourceTexts.length`. A hallucinated out-of-range index is dropped (same "don't trust unverifiable model output" rule as this pass's existing `entityRelations` handling); a response with no `source_indices` field at all degrades to salience 0 rather than failing schema validation. New `StoryEntity.salience Float @default(0)` column, persisted by `replaceStoryEntities` alongside `confidence`.
2. **Salience: not yet wired into `storyRelationScoring.ts`.** Computed and persisted now; changing `weightedEntityContainment`'s per-entity weight formula (currently pure IDF) to incorporate salience is a deliberate follow-up, not part of this ticket — that's a real scoring-design decision (how much should salience discount vs. IDF weight) that deserves its own reasoning once there's a concrete entity-page/wiki surface to validate it against, not a rushed addition here.
3. **Fuzzy search: built now, data-layer only.** First migration in this codebase to enable a Postgres extension (`CREATE EXTENSION IF NOT EXISTS pg_trgm`) plus a GIN trigram index on `Entity.canonicalName` (`entity_canonicalName_trgm_idx`), written as raw SQL — Prisma's schema DSL can't express an operator-class index, same convention as Coverage's partial unique index and StoryEntityRelation's CHECK constraint. No consuming query/endpoint/UI built here — an actual entity browse/search surface (presumably the first real piece of the wiki vision) is substantial enough to warrant its own ticket and design session, not a rider on a backend-audit remediation ticket.
4. **Scope stayed to salience + fuzzy search.** `EntityAlias` (cross-name-variant resolution) and `wikidataId` (external linking) are real parts of the same knowledge-graph vision but are identity/resolution concerns, different in shape from this ticket's presentation/search concerns — kept out, to get their own scoping session. Two forward-looking specs and five follow-up tickets covering the fuller vision were written in the same session per the user's explicit request: [docs/spec-entity-resolution.md](../../../docs/spec-entity-resolution.md) (entity aliasing, Wikidata linking → [ticket 40](../../news-triangulator/issues/40-entity-alias-merge.md), [ticket 41](../../news-triangulator/issues/41-entity-wikidata-linking.md)) and [docs/spec-entity-wiki.md](../../../docs/spec-entity-wiki.md) (entity browse/search UI, wiring salience into scoring → [ticket 42](../../news-triangulator/issues/42-entity-browse-search-backend.md), [ticket 43](../../news-triangulator/issues/43-entity-wiki-frontend.md), [ticket 44](../../news-triangulator/issues/44-salience-weighted-relation-scoring.md)).
