# 09 — Admin-action audit log

Type: grilling
Status: resolved
Blocked by: none — can start immediately

## Question

Spun out of [Quick fixes: no-brainers regardless of scale](01-quick-fixes-no-brainers.md) — **P2-24** confirmed real (no audit log of admin actions exists anywhere in the codebase today), but it's a new table plus wiring into 4 call sites (approve/reject Draft, approve/reject StoryRelation), not a one-liner alongside the actual quick fixes.

Decide:

1. What does a minimal audit-log row need — actor (admin user id), action type, target (Analysis/StoryRelation id), timestamp, and... anything else? The audit doesn't specify a shape, just that these actions "spend LLM money" and currently leave no trace.
2. Does this need its own admin-facing UI to view the log, or is "queryable via Prisma Studio" sufficient for now — same pattern as `LlmCallLog` (see `CONTEXT.md`'s "LLM Call Log" entry: "a maintainer's tool... inspected via Prisma Studio rather than surfaced anywhere in the app itself")?
3. Which 4 call sites get wired: `approveDraft`/reject-equivalent in `ingestionService.ts`, `approveStoryRelation`/`rejectStoryRelation`. Confirm this is the complete list — check for any other mutating admin action that spends money or changes state irreversibly.

## Answer

Resolved via a `/grilling` session (interactive, not self-answered) — recorded here in full since the interview reshaped the scope from the ticket's own starting assumption.

1. **Row shape**: `AdminActionLog { id, createdAt, actorId, action, targetType, targetId }` — matches this codebase's two existing maintainer-log-table precedents (`LlmCallLog`, ADR 0020; `MatchDecision`, ADR 0025) exactly: a plain `String` `action` column (not a Prisma enum) enforced by a closed TS union type at every call site, same convention as `LlmCallLog.callSite`/`LlmCallSite`. `targetType`/`targetId` is a generic pair, not a dedicated `analysisId`/`storyRelationId`/`userId` column each — one table covers every target kind today (`Analysis`, `StoryRelation`, `User`) and any future one without a migration. No FK relation from `actorId`/`targetId` into the live domain tables, matching `MatchDecision.candidateStoryId`/`candidateAnalysisId`'s own bare-string precedent — an FK to `User` would force an awkward choice between blocking user deletion (`Restrict`) or losing audit history when a user is removed (`Cascade`/`SetNull`), and a log's whole point is outliving its subject.
2. **No new UI — Prisma Studio only.** Two existing precedents for this exact shape of table (`LlmCallLog`, `MatchDecision`) both deliberately skip an in-app viewer; CONTEXT.md is explicit that `LlmCallLog` is "inspected via Prisma Studio rather than surfaced anywhere in the app itself." No new reason to diverge here.
3. **Library vs. hand-rolled**: hand-rolled, matching the same two precedents. No dominant, well-maintained "just add this" audit-log package exists for Prisma the way e.g. Rails has PaperTrail; the realistic alternative is a generic Prisma middleware auto-logging every mutation, which would over-capture (every `Coverage`/`Story` write, not just admin decisions) and lose the meaningful `action` semantics a short, explicit call-site list gives for free. Six columns and a dozen call sites is not what a library earns its keep on.
4. **Scope: 12 call sites, not the ticket's originally-assumed 4** — checked every `requireAdmin`-gated route, not just the ones P2-24's own text named:
   - **The original 4** (`ingestionService.ts`): `approveDraft`, `rejectDraft`, `approveStoryRelation`, `rejectStoryRelation` — reviewing an automated pipeline's output.
   - **User management** (`userService.ts`): `createUser`, `updateUser`, `deleteUser` — no LLM spend, but irreversible and security-sensitive. Initially proposed excluding these ("the consequence isn't self-evident unless you know the domain" was the reasoning for including the original 4, and its absence was — wrongly — the reasoning for excluding these). Corrected after pushback: gating what gets audited on whether a human reviewer would find the consequence "obvious" is the wrong test for anything security-relevant. In scope, unconditionally.
   - **The human-seeded submission flow** (`analysisService.ts`/`analysisStream.ts`, all `requireAdmin`-gated in this pre-launch phase): `createAnalysis`, `attachSeedToMatch`, `discoverSources`, `confirmCoverages`, `runAnalysisStream` (the SSE-streamed extraction+synthesis — the single most expensive LLM step in the whole pipeline). Same correction applies: "the Analysis/Coverage rows already record what happened" is the same shape of "consequence is legible elsewhere" reasoning already rejected for user management — dropped for consistency, all five included.

   Implementation-level refinement beyond the 12 conversation-level call sites, decided while wiring rather than re-opening the interview: `attachSeedToMatch` can itself trigger `approveDraft` internally (when the matched Analysis is still a Draft) — both log independently, under the same `actorId`, since they're two genuinely distinct facts (the admin's own action, and its downstream consequence), not one event double-counted. `createAnalysis`'s `'matched'` outcome (submission spends an embedding + a dedup-verification LLM call but creates nothing) is *not* separately logged — the money spent there is minor relative to every other action in scope, and there's no `Analysis` this outcome actually produced or mutated to attach a target to; logging against "the Analysis it matched" would misleadingly read as if the admin had acted on that Analysis when they hadn't yet (a subsequent `attachSeedToMatch`/`approveDraft` call, if the admin proceeds, is what actually does and gets logged). A deliberate, named cut, not a silent one.

Final action list (13 — `analysis.created`/`analysis.matched` split `createAnalysis`'s two outcomes into two distinct facts, everything else is one call site → one action): `draft.approved`, `draft.rejected`, `story_relation.approved`, `story_relation.rejected`, `user.created`, `user.updated`, `user.deleted`, `analysis.created`, `analysis.seed_attached`, `analysis.discovery_run`, `analysis.coverages_confirmed`, `analysis.synthesis_triggered` — 12 wired now; `analysis.matched` deliberately not (see above), kept in the type union for when/if that decision changes.

`analysis.synthesis_triggered` logs at the *start* of `runAnalysisStream` (the admin's request to synthesize is confirmed valid), not at completion — consistent with every other action here logging the admin's decision, never the pipeline's eventual downstream success/failure (matching how `draft.approved` logs the approval decision, not whether `entity.extract` later succeeds).

Recording failures never break the action they're logging — `recordAdminActionSafe`, same "a logging failure must never break the real call it's recording" convention as `recordMatchDecisionSafe`/`recordLlmCallSafe`.

A `/code-review` pass caught three real issues, all fixed: `runAnalysisStream` was awaiting the log write *before* `onReady()`, delaying the SSE response headers behind a DB round-trip for no benefit (moved after `onReady()`); `createUser`'s new parameter was named `actorId` while its two siblings (`updateUser`/`deleteUser`) use `requestingUserId` for the same concept (renamed for consistency); `attachSeedToMatch`'s two admin-action rows per click (`analysis.seed_attached` + `draft.approved` when it triggers `approveDraft`) had no comment explaining the double-log is intentional (added). A fourth finding — every new call site re-verifying the JWT cookie via `verifyAuthCookie(request)!.userId` instead of `requireAdmin` decorating `request` once — is real but predates this ticket (the same pattern already exists in `routes/adminUsers.ts`'s PATCH/DELETE handlers and `analyses.ts`'s `isAdmin` check). Fixing it means changing the shared auth plugin's contract across every `requireAdmin` route in the codebase — out of scope for an audit-log ticket. Left as-is, not actioned.
