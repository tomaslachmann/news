# 15 — Narrative generation as a queued job (supersedes ADR 0026's TTL fix)

Type: grilling
Status: resolved
Blocked by: 13

## Question

Split from [Thread aggregate](07-thread-aggregate.md) via [ADR 0028](../../../docs/adr/0028-pg-boss-job-queue-adoption.md). Moves narrative generation off `getAnalysisDetail`'s lazy-on-first-view trigger entirely, onto a job enqueued in the same transaction that marks an Analysis `COMPLETE` — matching how the tool-authored headline is already eagerly generated there (ADR 0021). This is the audit's originally-intended fix for P0-5 (§6: "Řešení: narrative generovat jako job... Zápis do DB pak slouží jako přirozený mutex napříč instancemi"); ticket 06 shipped a lighter interim fix (`narrativeGenerationFailedAt` + 24h TTL retry, ADR 0026) specifically *because* the queue was deferred at the time.

Not yet decided:

1. `narrativeGenerationFailedAt`'s role changes from "gates a read-endpoint's lazy retry" to "informs the job's own retry/backoff" — does `pg-boss`'s built-in retry config replace this field's purpose entirely (in which case: drop it, or keep it as an audit trail?), or does it still do real work (e.g. a longer cooldown than `pg-boss`'s own retry backoff would apply, for a case that's more likely a genuine content issue than a transient one)?
2. `getAnalysisDetail` currently returns `narrative: undefined` while generation is pending/hasn't run yet, and the frontend presumably renders "no narrative" the same way for "never attempted" and "failed." Once generation always happens at COMPLETE-time instead of first-view, does the reader ever see an Analysis mid-generation (COMPLETE but narrative not yet ready), and if so does the API/frontend need a distinct "generating" state, or is "no narrative yet" still an acceptable interim display?
3. `inFlightNarrativeGenerations` (the in-memory dedup Map) becomes entirely dead code once generation no longer happens in the request handler — confirm it's fully removable, not just unused in the common path.
4. Existing tests in `analysisService.test.ts` (the TTL-gating tests just added in ticket 06) test behavior this ticket removes — decide whether those tests get deleted outright or whether any of their assertions (e.g. "does not cache an empty narrative result") still apply to the job's own logic and should move rather than disappear.

## Answer

1. **`narrativeGenerationFailedAt`'s role**: kept, but purely as an audit trail — its only remaining reader-facing consumer (`getAnalysisDetail`'s TTL-gated regeneration check) is deleted outright, per ADR 0028 ("`getAnalysisDetail` becomes pure DB reads"). The job's own two failure paths (the LLM call throwing, and quote verification dropping every segment) still call `markNarrativeGenerationFailedSafe` before rethrowing, so "when did this Analysis last fail to narrate" stays visible in Prisma Studio the same way it was before — but nothing reads it back to decide whether to retry. `pg-boss`'s own `LLM_JOB_RETRY_POLICY` (ticket 13: `retryLimit: 3`, exponential backoff) is now the only retry mechanism. Accepted consequence, not a gap to fix here: an Analysis whose narrative generation fails all 3 attempts never gets a narrative — no 24h-cadence retry-forever the way the TTL marker gave it. This is a deliberate bounding (ADR 0028 explicitly supersedes ADR 0026's design, not just its trigger point), and matches this job's LLM-job retry policy exactly as applied to `entity.extract` (ticket 14) — a persistent failure spending indefinite retries was exactly what ADR 0026 itself was trying to avoid, just via a different mechanism.

2. **A reader visiting a COMPLETE Analysis before the job has run**: no distinct "generating" state added. `getAnalysisDetail` already renders "no narrative" (falls back to the structured-breakdown tabs) identically whether generation was never attempted, is still pending, or permanently failed — `AnalysisPage.tsx`'s `hasNarrative = !!narrative && narrative.length > 0` doesn't distinguish these today and this ticket doesn't ask it to. The window this exposes is short (queue pickup, one LLM call — typically single-digit seconds) and, unlike before this ticket, it never blocks a request: the previous lazy-on-first-view design made the *first* viewer's request itself wait out the LLM call inline. A future ticket can add SSE/polling for narrative readiness if this proves to be a real UX problem in practice; nothing here forecloses that.

3. **`inFlightNarrativeGenerations`**: fully removable, confirmed. It only existed to dedupe concurrent *requests* racing to regenerate inside `getAnalysisDetail`; once generation never runs from that read path, there is nothing left to dedupe there. (A retry racing a still-in-flight attempt of the *same* job is a different concern — `pg-boss` never runs two attempts of one job concurrently, so no replacement mechanism is needed.)

4. **Test migration**: every `getAnalysisDetail` test under the `NARRATIVE_RETRY_TTL_HOURS`/`generateAndCacheNarrative`/`inFlightNarrativeGenerations` umbrella (`analysisService.test.ts`, the block from "generates and caches the narrative..." through "deduplicates concurrent narrative generation...") is deleted — the behavior no longer exists. The "does not cache an empty narrative result" assertion (empty `segments` must not be treated as a successful, cacheable result) still applies and moves to the new `jobs/narrativeJob.test.ts`, along with a new assertion that this case is classified retryable (throws, rather than being silently swallowed the way the old read-endpoint helper had to swallow everything to always return a response).

**Enqueue site**: `completeAnalysisWithSynthesis` (`repositories/analysis.ts`) changes from an array-form `$transaction` to the interactive-callback form, gaining an optional `onComplete?: (tx) => Promise<void>` parameter — same seam `updateAnalysisStatusIfCurrently` already established for ticket 14's `entity.extract` enqueue, keeping job-queue concerns out of the repository layer (only the service layer ever imports `jobs/enqueue.ts`, per existing convention in `analysisStream.ts`'s sibling `ingestionService.ts`). `analysisStream.ts` passes a callback that enqueues `JobName.Narrative` with the transaction client, so a queue failure rolls back the COMPLETE transition itself — never a completed Analysis without its narrative job, mirroring ticket 14's Draft/`entity.extract` atomicity guarantee exactly. Unlike `entity.extract` (two call sites needing different `origin`/`coverageIds`), `narrative.generate`'s payload is just `{ analysisId }` — no per-call-site variation, so a single unconditional enqueue at the one completion call site is enough.

**Job handler error classification** (mirroring ticket 14's taxonomy): the Analysis (or its `SynthesisResult`) no longer existing is permanent — logged and swallowed, since nothing in this codebase ever deletes an Analysis today, this is a defensive guard, not a real path. Zero eligible source texts (no `OK` Coverage with `extractedText`) is also treated as permanent/no-op: by construction this can't happen on the real path (an Analysis can't reach COMPLETE without at least one such Coverage — `analysisStream.ts` fails the Analysis before Synthesis if none exist), and a retry can't manufacture `extractedText` that isn't there. Both the LLM call throwing and quote verification dropping every segment are retryable: marked via `markNarrativeGenerationFailedSafe` for the audit trail, then rethrown as `ExternalServiceError` so `registerJobWorker` reports `failed` and `LLM_JOB_RETRY_POLICY` actually retries — a fresh LLM call on retry isn't guaranteed to reproduce the same quote-verification failure.

Implemented on `ticket/audit-15-narrative-generation-job`.
