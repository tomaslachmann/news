# 17 — `Thread`/`ThreadMember` + `thread.recompute`

Type: grilling
Status: resolved
Blocked by: 13 (queue), 16 (`Story.eventTime`)

## Question

The aggregate itself, split from [Thread aggregate](07-thread-aggregate.md) via [ADR 0029](../../../docs/adr/0029-thread-aggregate.md), which settles the schema (`Thread`/`ThreadMember`, `ACTIVE`/`DORMANT`/`CLOSED`, `ORIGIN`/`DEVELOPMENT`/`REACTION`/`RESOLUTION`), the recompute mechanism (recursive CTE over `PUBLISHED` `FOLLOW_UP` edges, §8.6, `UNION` not `UNION ALL`, depth-capped at 50), and the `DORMANT → ACTIVE` revival approach (entity-configuration overlap via ADR 0024's tables, not a stretched candidate window). Not blocked by tickets 14/15 — `FOLLOW_UP` edges are already produced by the existing (for now still synchronous) relation-linking path regardless of when that itself moves to the queue.

Not yet decided:

1. `deriveThreadTitle` — the audit specifies "z Agreement napříč členy, ne z 1 titulku" (from Agreement across members, not one headline) but doesn't give a mechanism. Is this an LLM call (matching how the tool-authored Analysis headline works, ADR 0021 — same model? own `THREAD_MODEL` env var, matching ticket 11/12's per-pass-model precedent?) or a simpler derivation (e.g. the `ORIGIN` member's own generated headline, reused)?
2. `inferRole(member, index, total)` — the audit's pseudocode leaves this a black box. A plausible default: first member `ORIGIN`, last `RESOLUTION`, everything between `DEVELOPMENT` (with `REACTION` reserved for a member whose confirming `StoryRelation` reasoning indicates a response/reaction rather than a factual continuation) — needs a concrete rule, and confirmation this is presentation-only (never surfaced as an asserted fact the way ADR 0012 already guards against elsewhere).
3. Reader-facing surface: does ticket 37's existing "Related Events" section on the Article page gain a "this Event is part of a longer Thread" affordance now, or does this ticket build the data model only and leave the UI to a follow-up? (The Thread aggregate has no value to a reader until something displays it.)
4. `DORMANT → CLOSED` is manual-admin-action only per the audit's state diagram — does an Admin surface for this exist yet anywhere comparable (the Draft/StoryRelation review queues, tickets 36/09), or does this ticket need to add one?
5. `thread_active_idx`-style query needs — does anything read "all ACTIVE Threads" today (e.g. a homepage "ongoing stories" section), or is this schema built with no reader currently consuming it (worth flagging explicitly, matching this project's own audit §2.3 concern about Event Graph shipping before its reader surface did)?

## Answer

*Revised after a `/code-review` pass. It caught: a real crash bridging two pre-existing Threads (`ThreadMember.storyId`'s unique constraint, identical on every retry — no test had covered a component spanning two already-separate Threads); `findAgreementForTitle`/`runThreadTitlePass` running unconditionally on every recompute rather than only at Thread creation, contradicting point 1's own stated design below and spending a billed LLM call for nothing on every subsequent edge in an already-titled Thread; that same repo query not preserving the CTE's chronological order before feeding the LLM, when the prompt is explicitly told to expect chronological input; a misleading shared log message when only the (non-atomic, by design) `thread.recompute` enqueue failed, not the StoryRelation persistence it was bundled with; two independent DB reads awaited sequentially instead of concurrently in `getAnalysisDetail`; and the DORMANT-revival scope gap noted in point 4 below. All fixed except the DORMANT-revival gap, deferred explicitly instead — see point 4. Corrections folded into the answers below rather than kept as a separate erratum, except where a point's own history is worth keeping visible (point 4).*

1. **`deriveThreadTitle`**: an LLM call, reusing `SYNTHESIS_MODEL` (not a new dedicated env var — a one-off short title generation, run rarely, doesn't obviously need its own model tier the way per-Coverage extraction volume justified ticket 11/12's variable) and the exact same discipline `runHeadlinePass`/ADR 0021 already established: only Agreement `prose` ever reaches the prompt (never Contradiction/Framing/UniqueReporting), flattened across every member's own `SynthesisResult.dimensions.agreement` rather than one member's alone — "z Agreement napříč členy" taken literally. New `services/threadTitlePass.ts` + `prompts/threadTitle.txt`, structurally a near-duplicate of `headlinePass.ts` sized for "one arc, several stages" framing instead of "one event." Only ever called once, at Thread *creation* — the pseudocode's own structure (`title` set inside the `existing ?? create(...)` branch) never regenerates it as new members join, so a later member's Agreement never retroactively changes an already-published Thread's title. Fallback when every member's Agreement is empty (thin/early-stage Coverage across the board): the `ORIGIN` (earliest-`eventTime`) member's own resolved display title (`headline ?? seedHeadline`, the same `resolveDisplayTitle` fallback chain already used everywhere else) — never a blank/fabricated title, matching `Thread.title`'s NOT NULL schema.

2. **`inferRole`**: first member (by position) is `ORIGIN`; last is `RESOLUTION` **only when there are ≥3 members** (calling a bare second-of-two-members Story a "resolution" overclaims closure a 2-member arc hasn't earned — it stays `DEVELOPMENT`); everything strictly between is `DEVELOPMENT`. **`REACTION` is never inferred in v1** — detecting "this member is a reaction, not a factual continuation" reliably would need either fragile keyword-matching over `StoryRelation.reasoning`'s free text or an entirely new LLM classification call, disproportionate to a presentation-only positional label; `DEVELOPMENT` already covers this case honestly (a reaction is still a development in the arc). The enum keeps all four values (`ORIGIN`/`DEVELOPMENT`/`REACTION`/`RESOLUTION`) because ADR 0029's own Prisma model already declared it that way — only the *inference algorithm*, not the domain model, is narrowed here; a future ticket could add real `REACTION` detection without a schema change. **Presentation-only, confirmed, and — going further than "confirm this doesn't get asserted as fact" — not surfaced to the reader at all in this ticket** (see Q3): a role label like "this is the resolution" risks reading as the tool asserting narrative closure about a real event, exactly what ADR 0012 exists to prevent. `role` stays a DB/admin-visible field only for now; the reader-facing member list is unlabeled and chronological.

3. **Reader-facing surface: yes, now, minimally** — not a follow-up. The audit's own §2.3 ("nejdražší zjištění celého auditu": the Event Graph shipping with no reader surface at all) is a mistake this project already had to retroactively fix once (ticket 37, after `StoryRelation`/entities shipped invisible in tickets 34–36) — building `Thread` with no reader hook at all would repeat it knowingly. Scope kept proportionate to "the aggregate itself" (this ticket's own charter) rather than the audit's full "Etapa 6" criterion ("Reader UI: timeline linie místo plochého listingu" — a genuine UI redesign, real scope belonging to its own ticket): `AnalysisDetail` gains an optional `thread` field (`{ title, memberCount, members: [{ analysisId, title }] }`, ordered by position, `COMPLETE`-only members — same filter `relatedEvents` already applies, never linking to an unstable page) surfaced as a small addition to the Article page's existing Related Events section — not a dedicated `/thread/:slug` page, no homepage "ongoing storylines" section (that's Q5's still-unbuilt consumer). `role` is deliberately excluded from this payload (see Q2).

4. **`DORMANT → CLOSED` admin surface: out of scope, deferred with an explicit trigger** — no admin UI for this ships in this ticket. Unlike a Draft sitting unreviewed (real queue-buildup cost, tickets 09/36 exist because *someone* has to act) or a `PENDING_REVIEW` `StoryRelation` (same), a `DORMANT` Thread costs nothing left alone — it's simply inert until either a new `FOLLOW_UP` edge revives it or nothing ever does. Building a management page for a state transition nothing currently needs is exactly the speculative-generality ADR 0009 warns against. Trigger to revisit: an Admin actually asks to prune/archive old Threads, or `DORMANT` Thread count grows large enough to be worth curating — neither is true on a schema with zero Threads yet.

   **Also deferred, caught by `/code-review` rather than decided up front: `DORMANT → ACTIVE` revival via entity-configuration overlap.** ADR 0029's Decision section (and this ticket's own Question, quoting it) describes a *second* `DORMANT → ACTIVE` path beyond "a fresh in-window edge arrives" — a new Story matching a dormant Thread's aggregate entity configuration (ADR 0024's IDF-weighted containment) even *outside* `RELATION_CANDIDATE_WINDOW_HOURS` (14 days), so a case resuming after months doesn't require stretching that window for everyone. This ticket implements the DORMANT status transition itself (`upsertThreadFromComponent`, ≥30 days since the last member) and the ordinary revival path (any recompute of an already-DORMANT Thread's component flips it back to ACTIVE as a side effect of the normal status recomputation) — but **not** the entity-configuration matching pathway itself: nothing in `storyRelationScoring.ts`/`storyRelationPass.ts` checks a new Story's entities against dormant Threads outside the normal candidate window. A case genuinely resuming after >14 days will not be recognized and revived. This is a real, second matching pathway (a new candidate-generation route into `linkStoryRelations`, not a small addition to the existing one) — proportionate as its own ticket once a real multi-month-gap case is observed, not a bolt-on to this one. An earlier draft of this Answer and the map.md changelog entry both wrongly implied this was implemented ("per ADR 0029's... DORMANT-revival design") — corrected here and in map.md after a `/code-review` pass caught the gap between that claim and the actual diff.

5. **`thread_active_idx` (`[status, lastEventAt]`): added, unused for now — flagged explicitly, not silently shipped.** It exists because ADR 0029's own accepted Prisma model declares it, matching the schema literally rather than second-guessing an already-settled decision. But nothing in this ticket's own reader surface (Q3, a per-Story membership lookup keyed by `storyId`/`threadId`) queries "all ACTIVE Threads" — that's the homepage "ongoing stories" feature the audit's Etapa 6 criterion gestures at and this ticket doesn't build. Same honest gap the audit's own §2.3 flagged for Event Graph, now named up front instead of discovered later: this index has no consumer until that homepage feature (or something like it) exists.

**Enqueue design — deliberately not fully transactional, unlike tickets 14/15/16's writes.** `thread.recompute` (payload corrected from ticket 13's placeholder `{ threadId }` to the audit's own `{ seedStoryId }` — a Thread may not exist yet when the triggering edge is confirmed) is enqueued from both real trigger points ADR 0028 names ("a `StoryRelation` transitions to `type=FOLLOW_UP, status=PUBLISHED`"): `linkStoryRelations` (`storyRelationPass.ts`, the auto-linking path, `HIGH`-confidence `FOLLOW_UP`) and `approveStoryRelation` (`ingestionService.ts`, ticket 36's Admin approving a `LOW`-confidence `FOLLOW_UP` out of `PENDING_REVIEW`). Both call `enqueueJob` directly after their write succeeds, inside the same try/catch that already degrades-and-logs on any persistence failure at that point (matching `confirmCoverages`'s already-accepted non-atomic precedent, ticket 14 — not `completeAnalysisWithSynthesis`'s atomic-callback precedent, ticket 15/16). This is a deliberate downgrade from "never an X without its Y": unlike a missed `entity.extract`/`narrative.generate` enqueue (permanently loses that Analysis's own processing), a missed `thread.recompute` enqueue is **self-healing** for any component with ≥3 Stories — the recursive CTE (§8.6) expands the *whole* connected component regardless of which edge's enqueue actually fired, so the next confirmed edge anywhere in the same component still captures the missed one. The only real gap is an isolated 2-Story component whose one edge's enqueue fails and nothing else ever touches either Story — a soft "this pair's Thread enhancement never appears" degradation, not lost analysis work. Threading real transactional atomicity through `LinkStoryRelationsDeps`' caller-supplied function-reference injection (unlike `completeAnalysisWithSynthesis`, which already owned its own `prisma.$transaction` to extend) would mean reworking that whole deps-injection seam for a narrower, self-healing risk — not a proportionate trade for this ticket.

**Idempotency/concurrency of the recompute write itself** (not asked in the original "Not yet decided" list, but ticket 14 set the precedent that a new job type's own idempotency contract deserves an explicit answer): `upsertThreadFromComponent` wraps find-or-create + wholesale member replace + span/status update in one transaction, but is **not** lock-coordinated against a concurrent recompute for an overlapping component (two different seed Stories whose components both newly touch the same underlying arc, racing). `ThreadMember.storyId`'s `@unique` constraint is the actual safety net: the losing transaction's insert fails, throws, and `THREAD_RECOMPUTE_RETRY_POLICY`'s retry re-runs `findThreadByAnyStory` fresh, finding and joining the Thread the winner already created. Same judgment ticket 14 made for `entity.extract`'s own idempotency — trust retry over hand-rolled coordination for a narrow, self-healing race, rather than an advisory lock keyed on a component identity that isn't even known until the CTE resolves.

**Title-generation failures never spend `thread.recompute`'s own retry budget.** `deriveThreadTitle` (`threadRecomputeJob.ts`) catches any `runThreadTitlePass` error internally and falls back to the `ORIGIN` member's own display title, rather than letting it propagate and fail the whole job — `THREAD_RECOMPUTE_RETRY_POLICY` (ticket 13) was sized for a cheap, deterministic, DB-only job (10 retries, short fixed delay); a Thread-creation run now makes one LLM call, and treating an LLM hiccup as a job failure would mean retrying a billed call up to 10 times for a presentation-only title. `JOB_RETRY_POLICY` itself is left unchanged.
