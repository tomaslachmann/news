# Spec — Event Graph: Story Relations & Entity Signals

**Triage label:** ready-for-agent

## Problem Statement

Today, every completed Analysis ("Article") is presented the same way — a single, isolated entry in a flat, reverse-chronological listing (`HistoryPage`). When a real-world event unfolds over several days across several separate news cycles — a detention, then an official's statement about it, then the other side's response — each stage becomes its own unrelated-looking Story with its own Article. A reader who opens one has no way to discover that it's part of a larger thread, or to navigate to what came before or after it, without already knowing to search for it themselves. The tool's whole premise is helping a reader see the shape of coverage clearly; right now that clarity stops at the boundary of a single event and doesn't extend to how events connect to each other.

## Solution

Introduce a lightweight **Event Graph**: typed, directional relationships between Stories (`StoryRelation`) that let a reader navigate from a completed Article to what's directly related to it — a follow-up development or a topically related event — without hunting through the flat listing. Relations are found cheaply (embedding similarity + a lightweight entity/entity-relation overlap signal + time proximity) to shortlist a handful of candidates, and only that shortlist gets an actual LLM confirmation call, which returns a relation type from a small closed set, a plain-language reason, and a HIGH/LOW confidence tier. HIGH-confidence relations publish immediately; LOW-confidence ones go through a new Admin review queue — mirroring how the existing Ingestion Draft queue already gates uncertain material before it reaches a reader — rather than showing a reader a possibly-wrong connection.

To make that candidate shortlist smarter than pure text similarity, each Story also gets a small set of extracted named entities and entity-to-entity relations (e.g. "Donald Tusk REPRESENTS Poland"), generated once as Story-scoped evidence. This is explicitly *not* a knowledge graph and *not* authoritative real-world identity resolution — it's a cheap structural signal that two Stories mentioning the same entities in the same relational shape are more likely describing the same unfolding event than two Stories that merely share a topic.

`Story`'s reader-facing name becomes **"Event"**, mirroring how `Analysis`'s reader-facing name is already "Article" — the same presentation-only pattern, not a renaming of the underlying entity.

## User Stories

1. As a Reader, I want to see which other Events are directly related to the one I'm reading, so that I can follow a developing story without manually searching for it.
2. As a Reader, I want related Events to be labeled by how they relate (a follow-up vs. a merely related event), so that I understand the nature of the connection, not just that one exists.
3. As a Reader, I want to see a short, plain-language reason why two Events are linked, so the connection is traceable, not an unexplained black-box suggestion — consistent with how every claim in this tool already traces back to a source.
4. As a Reader, I want the tool to never assert that one Event *caused* another, so it doesn't make an interpretive/causal claim beyond what's verifiable — matching the project's existing refusal to declare a winner or assert disputed content as fact (ADR 0012).
5. As a Reader, I want only relations the tool is reasonably confident about to be shown to me, so I'm not shown speculative or wrong connections between unrelated Events.
6. As a Reader, I want each related Event shown with its own title and source count, so I can decide whether to follow the link without clicking in blind.
7. As a Reader, I want the public listing and Article page to keep working exactly as they do today for any Event that has no relations yet, so this feature is additive and never breaks the existing experience.
8. As an Admin, I want to review and confirm or reject lower-confidence relations before they're shown to readers, so uncertain connections get a human check, mirroring how Drafts already work.
9. As an Admin, I want the relation-review queue to live on the same Admin surface as the existing Ingestion review queue, so I have one place to check for anything needing my attention.
10. As an Admin, I want a rejected relation recorded as rejected, not silently deleted, so the same candidate pair doesn't get re-surfaced for review on a later pass.
11. As a Maintainer, I want relation candidates generated cheaply (embedding + entity overlap + entity-relation overlap + time proximity) before any LLM call happens, so we don't pay LLM cost comparing every Story against every other Story.
12. As a Maintainer, I want the LLM confirmation call for a relation to return a categorical confidence tier (HIGH/LOW), not a raw numeric score, so nothing surfaced to a reader or Admin is a magic number nobody can act on or explain.
13. As a Maintainer, I want relation-candidate generation and entity extraction to run before Extraction/Synthesis for every Story — Draft approval for Ingestion-originated Stories, Review Step confirmation for human-seeded Stories — so no new LLM cost is added to Ingestion's per-item hot path (ADR 0018), and both paths get the richest source text realistically available to them at that point in their respective pipelines.
14. As a Maintainer, I want entities and entity-to-entity relations stored as Story-scoped evidence (a JSON field), not a global knowledge graph, so the system doesn't take on real-world entity-resolution complexity it doesn't need for its actual goal — grouping coverage into one Event, not building an entity database.
15. As a Maintainer, I want each extracted entity to carry a deterministic canonical key derived from its LLM-normalized name, not an LLM-invented identifier, so the same real-world entity mentioned in two different Stories reliably produces the same key without relying on the LLM being self-consistent across separate calls.
16. As a Maintainer, I want it documented that a canonical key is a deterministic label, not a guarantee of correct real-world identity resolution (name collisions across different real-world referents — e.g. two different people who happen to share a surname — are a known, accepted v1 limitation), so nobody later assumes it's more authoritative than it is.
17. As a Maintainer, I want each extracted entity and entity-relation to carry its own extraction-confidence value, used only as an internal scoring input, so noisier extractions can be weighted down in candidate scoring without ever being surfaced to a reader or Admin as a raw number.
18. As a Maintainer, I want entity-to-entity relation types constrained to a small, closed, predefined enum — not free text the LLM invents — so relation types stay comparable across Stories instead of drifting into unbounded near-duplicate labels.
19. As a Maintainer, I want it explicit that an entity-relation is what one Story's coverage asserts, not a general/global fact about the entities involved (e.g. "met with" is true of this specific event, not a permanent property of the two people), so the data model doesn't imply more permanence than it has.
20. As a Maintainer, I want `Story.anchorHeadline`, `Analysis.seedHeadline`, and `SynthesisResult.headline` left completely untouched by this feature, so this work doesn't regress already-shipped same-event matching (ADR 0017/0018/0019) or headline generation (ADR 0021).
21. As a Maintainer, I want Ingestion's existing per-item hot-path matching (`findBestMatch`, `MATCH_THRESHOLD`, `DEDUP_WINDOW_HOURS`) left unmodified, so relation-candidate generation is additive, using its own separate constants, not a rework of already-working duplicate detection.
22. As a Maintainer, I want existing tests for `approveDraft`, `createAnalysis`, `findBestMatch`, and the Ingestion review queue to keep passing without meaningful behavior changes beyond whatever this feature's new step requires, so it doesn't destabilize the existing pipeline.

## Implementation Decisions

- **New Prisma model `StoryRelation`**: `id`, `fromStoryId`/`toStoryId` (FKs to `Story`), `type` (enum: `RELATED` | `FOLLOW_UP`), `confidenceTier` (enum: `HIGH` | `LOW`), `reasoning` (`String`), `status` (enum: `PUBLISHED` | `PENDING_REVIEW` | `REJECTED`), `createdAt`. A directional edge (the newer Story is `fromStoryId`, the candidate it matched against is `toStoryId`), but read bidirectionally for display — a Story's "related Events" query checks both `fromStoryId` and `toStoryId`.
- **`Story.entities: Json`** (default empty array) — one entry per extracted entity: `{ key, name, type, confidence }`, where `type` is one of `PERSON` | `ORGANIZATION` | `PLACE` | `COUNTRY`.
- **`Story.entityRelations: Json`** (default empty array) — one entry per extracted entity-to-entity relation: `{ from, to, type, confidence }`, where `from`/`to` are entity keys and `type` is drawn from a small closed enum (candidate list: `REPRESENTS`, `HOLDS_POSITION_IN`, `WORKS_FOR`, `MEMBER_OF`, `LOCATED_IN`, `BASED_IN`, `PART_OF`, `INVOLVES`, `MEETS`, `ATTACKS`, `ACCUSES`, `ANNOUNCES` — exact final set, likely 8–12 of these, decided at ticket-breakdown time).
- **No new Entity/EntityRelation tables** — both fields are Story-scoped JSON, not a queryable global entity registry. This is a deliberate simplicity choice, not an oversight (see Out of Scope).
- **Canonical key derivation**: the entity-extraction LLM call returns `{ mention, canonical_name, type }` per entity — it normalizes the name (resolving "Tusk" and "Donald Tusk, Polish PM" to the same `canonical_name`, using its own world knowledge) but never invents a key or asserts global identity. The backend derives `key` deterministically: `type + ':' + slugify(canonical_name)`. Same normalized name always produces the same key, independent of which call produced it — a pure function, no LLM involvement in key generation itself.
- **`key` is a deterministic label, not verified identity.** Two different real-world entities that happen to normalize to the same name (e.g. two unrelated people who share a surname) can collide under this scheme — an accepted, documented v1 limitation. A future entity-resolution/aliasing layer could disambiguate this without changing today's data shape.
- **Entity-relations are Story-scoped assertions**, not global facts — `Story.entityRelations` records what *that Story's coverage* asserts about two entities, not a permanent property of them.
- **New pass module `entityExtractionPass.ts`**: one `callJsonModel` call per Story. Output = `{ entities: [...], entityRelations: [...] }`, validated against a zod schema with closed enums for `type`. New `LlmCallSite` value (`'entityExtraction'`), automatically covered by the existing durable call-logging (ADR 0020) with no extra wiring.
- **No backfill**: existing Stories keep `entities`/`entityRelations` empty (never retroactively extracted) — same convention as the headline feature's (ADR 0021) no-backfill decision.
- **New pass module `storyRelationPass.ts`**: given a Story and one shortlisted candidate Story, one `callJsonModel` call asks the LLM to judge whether/how they're related — `{ related: boolean, type: 'RELATED' | 'FOLLOW_UP', confidenceTier: 'HIGH' | 'LOW', reasoning: string }` on a match, or `{ related: false }`. Mirrors `storyVerification.ts`'s boolean-verdict shape, extended with a type/tier choice instead of a single boolean. New `LlmCallSite` value (`'storyRelation'`).
- **Deterministic candidate scoring**: a new function (alongside `findBestMatch` in `storyMatching.ts`, or a sibling module) ranks a widened pool of recent Stories by `embeddingSimilarity + entityKeyOverlap + entityRelationOverlap + timeProximity` and returns the top ~20. Its own time window and threshold, distinct from `DEDUP_WINDOW_HOURS`/`MATCH_THRESHOLD` — those are tuned for "is this literally the same event," this is tuned for "is this a related-but-distinct event, possibly days later." Only the top handful (e.g. 3–5) of the ranked shortlist gets an actual `storyRelationPass` call. Exact weights/window/threshold/shortlist-size are implementation-time tunable constants, same convention as `MATCH_THRESHOLD`/`MIN_VISIBLE_SOURCE_COUNT` — not pinned by this spec.
- **Candidate direction**: relation-candidate generation runs once, when a Story becomes visible (see trigger points below), searching *backward* against already-visible, recent Stories. Existing Stories are never retroactively re-scanned — they simply accumulate incoming edges as later Stories reference them.
- **Trigger points** (both stay before Extraction/Synthesis, so the Q5-era timing decision is unchanged; no new cost lands on Ingestion's hot path):
  - Ingestion-originated Stories: inside `approveDraft`, alongside the existing pre-Extraction quality gate (ticket 24). Input = the Story's `anchorHeadline` plus the RSS titles of every Coverage attached by that point (typically ≥2, since a Draft isn't Admin-visible below `MIN_VISIBLE_SOURCE_COUNT`).
  - Human-seeded Stories: inside `confirmCoverages` (Review Step confirmation), not `createAnalysis` — `createAnalysis` only has the single seed article's scraped title/excerpt at that point, while `confirmCoverages` already scrapes every confirmed source's full text as part of its own existing flow. Running entity extraction there means the human-seeded path gets real multi-source `extractedText` as input — richer than what's available to it at creation time, and richer than the Ingestion path's RSS-titles-only input at its own trigger point. Still strictly before Extraction/Synthesis. Low-volume, real-time flow, so the extra cost isn't the ADR 0018 hot-path concern (that's specifically about Ingestion's high-frequency polling).
- **Failure handling**: a failure in entity extraction or relation-candidate generation/confirmation degrades gracefully — logged, entities/entityRelations left empty, no `StoryRelation` created for that pass — rather than blocking `approveDraft` or `confirmCoverages`. Mirrors `createAnalysis`'s existing embedding-generation failure handling (a missing signal is worse than blocking submission/confirmation, but not worth failing the request over).
- **`StoryRelation` uniqueness/idempotency**: `@@unique([fromStoryId, toStoryId])`. If the generation step ever re-runs for a Story (e.g. a retried request), it must not create a second row for the same pair — check for an existing row (either direction) before inserting.
- **Candidate pool status**: relation-candidate scoring considers recent Stories of any `Analysis` status (mirrors `findRecentStoriesForMatching`'s existing "every status" philosophy, ADR 0018) — cheap to compute regardless of whether the candidate is finished yet. Display-side filtering (below) is where status actually matters.
- **Display filtering**: the Article page's "Related Events" section (ticket scope below) only shows `PUBLISHED` `StoryRelation`s where the *other* Story's Analysis is `COMPLETE` — nothing links to a Draft/PENDING page that isn't a stable Article yet. A `StoryRelation` to a non-COMPLETE Story still exists in the database; it simply isn't surfaced in this wave's UI. Showing in-progress related threads is explicitly part of the deferred `Story.status`/ranking wave, not this one.
- **Admin review queue resilience**: if the *other* Story's Analysis status changes after a `StoryRelation` was generated (e.g. it later fails), the review queue and its confirm/reject actions still work — display degrades gracefully (e.g. shows the working title either way via `resolveDisplayTitle`), never errors.
- **Publish gating**: a `HIGH`-confidence `storyRelationPass` result creates a `StoryRelation` with `status: PUBLISHED` immediately, visible to readers right away. A `LOW`-confidence result creates one with `status: PENDING_REVIEW`, invisible to readers until an Admin acts on it.
- **New Admin actions**: confirm (`PENDING_REVIEW` → `PUBLISHED`) and reject (`PENDING_REVIEW` → `REJECTED`, permanent — never re-surfaced or re-generated for the same pair), mirroring `approveDraft`/`rejectDraft`'s shape.
- **New Admin UI + API**: a third section on `IngestionReviewPage.tsx` listing `PENDING_REVIEW` `StoryRelation`s, mirroring `DraftsSection`'s list-plus-action-buttons pattern (each showing both Stories' display titles, the proposed type, and the reasoning string). New endpoints mirroring the Draft approve/reject shape: list pending relations, confirm one, reject one. New shared type (e.g. `PendingStoryRelationItem`) mirroring `PendingAdditionItem`'s shape — both Stories' display titles, type, reasoning, createdAt.
- **Article page + API**: `AnalysisPage.tsx` gains a "Related Events" section listing `PUBLISHED` `StoryRelation`s for the current Story (either direction, other side `COMPLETE` only — see Display filtering above), each showing the related Story's own display title (reusing `resolveDisplayTitle`/the `title` field already shipped in ticket 33) and source count. Surfaced via a new field on `AnalysisDetail` (e.g. `relatedEvents: RelatedEventItem[]`), populated by `toAnalysisDetail`, not a separate endpoint — one round-trip for the whole Article page, consistent with how the rest of that page already loads.
- **"Event" terminology**: introduced as `Story`'s reader-facing name in any new user-facing copy this feature adds, mirroring the existing Article/Analysis pattern. Does not rename `Story` in code. `CONTEXT.md` gets a new entry documenting this, added during implementation (matching this project's established practice — see ADR 0021/CONTEXT.md's `Headline` entry, added when ticket 32 was implemented, not during its spec).
- **New ADR expected at implementation time**, documenting: the `RELATED`/`FOLLOW_UP`-only decision against `CAUSES` (ADR 0012), the entities-as-Story-scoped-JSON-not-global-table decision, and the deterministic-key-not-verified-identity decision.

## Testing Decisions

Tests only external behavior, matching every existing pass in this pipeline.

- `entityExtractionPass.ts` / `storyRelationPass.ts`: unit-tested by mocking `callJsonModel`, mirroring `headlinePass.test.ts` / `extractionPass.test.ts`'s pattern — assert exactly what's sent as input, that the response is validated against its zod schema (closed enums rejected if the model returns something outside them), and that a valid response passes through unmodified.
- The deterministic candidate-scoring function and the canonical-key derivation: pure functions, unit-tested directly with no mocking — mirroring `storyMatching.test.ts`'s direct testing of `findBestMatch`.
- `approveDraft`'s and `confirmCoverages`'s new entity-extraction/relation-generation step: tested at the service layer via repository mocks, mirroring `ingestionService.test.ts` / `analysisService.test.ts`'s existing pattern — asserting the new step runs at the right point, and that a failure in it degrades gracefully without blocking the existing approval/confirmation flow.
- `StoryRelation` persistence (creation at the right `status` per confidence tier, confirm/reject transitions) integration-tested against a real, ephemeral Postgres instance via testcontainers, mirroring `test/integration/analysis.test.ts`'s established pattern.
- The new Admin confirm/reject actions: tested at the service layer, mirroring `ingestionService.test.ts`'s existing `approveDraft`/`rejectDraft` tests.
- Frontend: no new test infrastructure — the "Related Events" section and the new Admin review section render already-tested, backend-shaped data, matching ticket 33's precedent (vitest is configured for the frontend package but no component tests exist yet in this codebase; this spec doesn't change that).

## Out of Scope

- `Coverage.sourceRole` (PRIMARY/SECONDARY/FOLLOWUP/ANALYSIS/REACTION classification) — named future wave, not built here.
- `Story.status` lifecycle (`EMERGING`/`ACTIVE`/`QUIET`/`ARCHIVED`) — named future wave.
- `storyScore` ranking and any homepage/listing redesign (grouping the public listing by Event instead of a flat Article list, "Developing" indicators, update-velocity tracking) — named future wave; `HistoryPage`'s current flat, reverse-chronological listing is unchanged by this spec.
- `primaryCategory`/`country` fields on `Story`, and the `topicSimilarity`/`locationSimilarity` terms of a fuller candidate-scoring formula that would depend on them — deferred until those fields exist in a future wave. This spec's candidate scoring uses only embedding similarity + entity overlap + entity-relation overlap + time proximity.
- `CAUSES` (and `REACTION`/`DEVELOPMENT`) as `StoryRelation` types — deferred. Asserting causation between two real-world events is closer to the kind of interpretive claim ADR 0012 exists to keep this tool from making than `RELATED`/`FOLLOW_UP` are. Revisit once those two types have real production data to evaluate.
- A global, cross-Story entity-resolution/aliasing layer — a real `Entity` table, fuzzy name matching, disambiguating same-name-different-referent cases (e.g. "Washington" the place vs. a person surnamed Washington). `Story.entities`/`Story.entityRelations` stay Story-scoped JSON evidence in this wave; the deterministic key scheme is designed so this layer can be added later without a data-shape migration.
- `canonicalTitle`/`canonicalSummary` for a Story that stays stable across retitling as coverage evolves (raised in the original proposal) — not part of this spec; `Story.anchorHeadline` stays exactly as it is today.
- Any change to `Story.anchorHeadline`, `Analysis.seedHeadline`, or `SynthesisResult.headline`'s existing role, values, or generation logic.
- Any change to Ingestion's existing per-item hot-path matching (`findBestMatch`, `MATCH_THRESHOLD`, `DEDUP_WINDOW_HOURS`, `MIN_VISIBLE_SOURCE_COUNT`) — relation-candidate generation is a separate, additive step with its own constants.
- The exact `entityRelations` type enum size (8–12 candidates listed above) and exact candidate-scoring weights/window/threshold/shortlist-size — left as implementation-time tunable constants, same convention as `MATCH_THRESHOLD`/`MIN_VISIBLE_SOURCE_COUNT`, to be finalized during ticket breakdown rather than locked here.

## Further Notes

Produced via a `/grill-with-docs` session (2026-08-17–18), triggered by a detailed, unsolicited "Event Graph" proposal, reasoned against the current, already-shipped Story/Coverage/Analysis matching pipeline (ADR 0017/0018/0019) and the project's core "never assert beyond what's verifiable" principle (ADR 0012). The session went through several rounds of refining the entity-storage shape (plain strings → a table → Story-scoped JSON with deterministic keys) before converging on the design recorded here.

Two defaults were inferred by the spec-writer rather than independently confirmed with the user, flagged here per this project's established practice for such gaps (see ticket 32/33's spec for precedent):

- The failure-handling default for entity/relation extraction (degrade gracefully, don't block `approveDraft` or `confirmCoverages`) mirrors `createAnalysis`'s existing embedding-generation failure handling, but wasn't explicitly re-confirmed in the grilling session.
- The exact criteria the relation-confirmation LLM call uses to choose `HIGH` vs `LOW` confidence is left to prompt design at implementation time — only the two-tier categorical shape itself (not a numeric score) was confirmed.

"Event" as `Story`'s reader-facing name applies to any future UI work touching Story display, not only this spec's own "Related Events" section.
