# ADR 0025 — Canonical embedding input, and a content-addressed embedding cache

## Status
Accepted

## Context
`docs/audit.md` P1-8 (folded into the wayfinder map's [Retrieval/matching architecture](../../.scratch/backend-audit/issues/05-retrieval-matching-architecture.md)) found that `storyMatching.ts`'s `buildEmbeddingInput` looks unified across Ingestion and human-seeded submission — both call the same function — but the *distributions* feeding it are not: Ingestion passes `title + item.contentSnippet` (an RSS teaser, typically one or two lines of marketing lead), while human-seeded submission passes `scraped.title + excerpt`, where `excerpt` is `articleScraper.ts`'s "first 3 lines over 40 characters from Readability's `textContent`" — real article prose, a different length and register entirely. ADR 0019's premise — that both paths share one same-event classification mechanism — is undermined at the input level: a cross-path match (human ↔ Ingestion) is systematically weaker than an Ingestion ↔ Ingestion match, making `MATCH_THRESHOLD = 0.75` effectively two different thresholds depending on which side of a pair is being compared.

Separately, `Story` carries no record of which `EMBEDDING_MODEL` or which exact input produced its stored `embedding` — a mid-flight model change silently mixes incomparable vectors into the same matching pool, undetectable after the fact (same dimension: silent noise; different dimension: `cosineSimilarity`'s own length guard forces a score of 0, no error, no signal).

While fixing input construction, the ticket 05 grilling session also decided to add real embedding-call idempotence, not just an audit trail: a retried Ingestion poll, a duplicate submission, or two outlets syndicating byte-identical wire copy all produce the exact same canonical input text, and `generateEmbedding` is deterministic for a fixed model — so re-calling the embeddings API for input already embedded is pure waste. This can only work as a cache keyed by `(model, inputHash)` checked *before* an embedding exists on any Story, not as a lookup against `Story`'s own stored hash — a retry or duplicate is typically caught before any Story is created for it at all.

## Decision
**One canonical input-construction path.** `buildEmbeddingInput` (`storyMatching.ts`) normalizes whitespace, strips a small set of known RSS-teaser boilerplate prefixes ("Foto:", "Video:", "Ilustrační snímek:", "Reklama:"), and caps the lead/excerpt at a fixed length before concatenating it with the title. Both call sites (`ingestionService.ts`, `analysisService.ts`) already route through this one function — the fix is entirely inside it, not a new call-site-specific branch.

**`Story.embeddingModel`/`Story.embeddingInputHash`** record which model and which exact (hashed) input produced the stored vector — nullable, since every Story created before this ticket has neither. Audit-only: nothing reads these back to gate matching; they exist so a future `EMBEDDING_MODEL` change, or a bug in input construction, is detectable by inspection instead of silently corrupting the matching pool.

**A new `EmbeddingCache` table**, keyed on `(model, inputHash)` → the embedding vector, checked *inside* `generateEmbedding` (`embeddingClient.ts`) itself — transparent to every caller, not duplicated at each of the two call sites. A cache hit returns the stored vector without calling the embeddings API, and — deliberately — without writing an `LlmCallLog` row: `LlmCallLog` is a record of one LLM call (ADR 0020), and a cache hit is specifically the case where no call happened. A miss behaves exactly as today (API call, `LlmCallLog` row on success or failure) and additionally writes the result into `EmbeddingCache`.

Storing the raw vector in `EmbeddingCache` does not reopen ADR 0023 (which kept the raw vector out of `LlmCallLog`): that decision was about a *debug log*, where a vector has ~no per-byte debugging value next to the text such a log otherwise holds. Here the vector is the cache's entire payload — there is nothing to serve the cache's purpose except storing exactly that. `EmbeddingCache` is unbounded, with no pruning job, the same accepted posture as `LlmCallLog` (ADR 0020) — revisit only if it's ever shown to matter.

Not built now: linking a cache write, or a `MatchDecision` row (ADR-adjacent but not itself ADR-worthy — see the ticket's Answer section), back to the specific `LlmCallLog` row that produced a given vector. Nothing in this ticket's scope needs that traceability; the outcome (matched or not, and — on the human-seeded path — the LLM's confirmation) is what calibration needs, not a foreign key to the raw call.

## Consequences
- Every embedding request (Ingestion's per-item match, human-seeded submission's dedup check) now passes through exactly one normalization function and one cache check, regardless of call site — a future third call site gets both for free by calling `generateEmbedding`, with nothing extra to remember.
- `generateEmbedding`'s return shape changes from a bare vector to `{ vector, model, inputHash }`, so a caller that wants to persist `Story.embeddingModel`/`embeddingInputHash` has what it needs without a second, redundant hash computation. Every existing caller is updated in the same change.
- A retried or duplicate embedding request for identical input is now free (no API call, no new `LlmCallLog` row) after the first — the cost/latency win the ticket's session specifically asked for, not merely storage for later inspection.
- Changing `EMBEDDING_MODEL` naturally produces a wave of cache misses (the key includes `model`) rather than silently reusing a differently-distributed vector — the cache's own keying is itself a partial mitigation of the "silent model mix" half of P1-8, on top of the explicit `Story.embeddingModel` audit trail.
- `MATCH_THRESHOLD = 0.75` was tuned (informally) against the old, asymmetric inputs; changing input construction shifts the embedding distribution it's being compared against. The dev database is empty, so this is a clean cutover with nothing to migrate or re-embed — a real production deployment revisiting this later would need to treat it as a breaking change to the matching pool, not an invisible one.
