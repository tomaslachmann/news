# ADR 0022 — Story-relation data model: JSON entity evidence, closed relation types, categorical confidence

## Status
Accepted

## Context
Ticket 34 introduced a lightweight entity signal (`Story.entities`, `Story.entityRelations`) as candidate-scoring evidence, and ticket 35 builds the actual Story-to-Story relation-linking pass (the "Event Graph") on top of it. Three design decisions from those tickets are hard to reverse once other code depends on their shape, and are non-obvious enough to a future reader that they're recorded here rather than only in code comments.

This work followed a `/grill-with-docs` session (2026-08-17–18) that started from a much larger proposal — a full entity/relation knowledge graph with its own tables, a richer relation-type taxonomy including causal types, and numeric confidence scores. The session progressively narrowed that proposal against this project's existing constraints (ADR 0012, ADR 0018) down to what's actually implemented.

## Decision

**Entities/entity-relations are Story-scoped JSON, not a global `Entity` table.** `Story.entities` and `Story.entityRelations` are JSON columns holding evidence for *this Story's own coverage*, not a queryable, deduplicated, cross-Story entity registry. A real `Entity` table would require solving entity resolution — deciding whether "Tusk" in one Story and "Donald Tusk" in another are the same real-world person, or whether "Washington" means the place or a person — which is itself a hard, separate problem this feature doesn't need to solve to achieve its actual goal: grouping coverage into one Event, not building an entity database. Each entity instead gets a `key` deterministically derived as `type + ':' + slugify(canonical_name)` (`entityKey.ts`) — the LLM normalizes a mention to its fullest known form but never invents the key itself, so the same real-world entity mentioned identically in two different Stories reliably produces the same key without depending on the LLM being self-consistent across separate calls. This key is a deterministic label, not a verified real-world identity: two different real-world entities that happen to normalize to the same name (two people sharing a surname, or a place and a person sharing a name) can collide. This is an accepted, documented v1 limitation — entity overlap is one weak signal among several in relation-candidate scoring (`storyRelationScoring.ts`), never a source of truth on its own, and a future entity-resolution/aliasing layer could disambiguate this without changing today's data shape.

**`StoryRelation.type` is limited to `RELATED` and `FOLLOW_UP`.** The original proposal's fuller taxonomy included `CAUSES`, `REACTION`, and `DEVELOPMENT`. Asserting that one real-world event *caused* another is an interpretive claim about the world — precisely the kind of claim ADR 0012 already keeps this tool from making anywhere else (the Cross-Source Narrative never adjudicates a disputed fact; Extraction separates factual claims from interpretive statements). A causal relation type would let the tool make exactly that kind of claim about *events themselves*, just at a different altitude than a single Coverage's claims. `RELATED` (topical/entity overlap, no claimed direction) and `FOLLOW_UP` (a later development of the same unfolding situation) don't have this problem — neither asserts a causal mechanism, only a topical or chronological relationship a reader can independently verify from the two headlines. `CAUSES`/`REACTION`/`DEVELOPMENT` remain a named, deferred extension, revisitable once `RELATED`/`FOLLOW_UP` have real production data to evaluate against.

**Relation confidence is categorical (`HIGH`/`LOW`), not a raw score.** No other reader- or Admin-facing surface in this codebase shows a raw LLM-generated number as if it were meaningful on its own (`MATCH_THRESHOLD`, `MIN_VISIBLE_SOURCE_COUNT`, and this ticket's own scoring weights are all internal tunable constants, never surfaced). A `confidence: 0.73` on a relation invites exactly that misreading. The two-tier categorical shape mirrors `storyVerification.ts`'s existing `{sameEvent: boolean}` precedent, extended with one more tier: `HIGH` publishes a relation immediately, `LOW` routes it to an Admin review queue (ticket 36) before a reader ever sees it — the confidence tier does real gating work, rather than being a display-only number. (Per-entity/per-entity-relation extraction confidence, added in ticket 34, is a different, lower-level concept: a raw float used only internally as a candidate-scoring input, never surfaced to a reader or Admin — it doesn't conflict with this decision, it just isn't subject to it.)

## Consequences
- Relation-candidate scoring (`storyRelationScoring.ts`) treats entity/entity-relation overlap as one signal among several (alongside embedding similarity and time proximity), never the sole or authoritative basis for a match — consistent with the key-collision limitation above.
- No entity-resolution/aliasing layer exists yet. If entity-key collisions turn out to matter in practice (noisy candidate scoring from unrelated same-named entities), the fix is an additive layer on top of the existing deterministic key, not a data-shape migration.
- A relation between two Stories can never encode "A caused B" — only that they're topically related or that one followed the other. A reader who wants to judge causation has to do so themselves from the two Articles' own content, exactly as they already do for a single Article's Contradiction/Framing dimensions.
- `StoryRelation.confidenceTier` is the only relation-level number-like field exposed anywhere in this feature, and it's an enum, not a float — there is no raw relation-confidence score anywhere to migrate away from later if this proves too coarse; widening it to a third tier is additive, not a breaking change.
